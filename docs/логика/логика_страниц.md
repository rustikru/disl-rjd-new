# Пользовательские KPI — группировка и детализация

Пользовательские KPI сохраняют условия в `XX_ETW.XX_RJD_KPI_TBL.WHERE_CONFIG`.
Для `TABLE` открывается стандартная детализация. Для группировки доступны только
фиксированные шаблоны `TRAIN_NUMBER` (по номеру поезда) и `TRAIN_INDEX`
(по индексу поезда). Их определения находятся в
`src/Reports/KpiGroupingTemplates.php`; в Oracle сохраняется только код шаблона
в `WHERE_CONFIG.detail.template`.

`ApiController::dislDetail()` применяет условия KPI, группирует вагоны по полю,
заданному шаблоном, и возвращает сводные показатели, маршрут и фиксированные
поля группы. Раскрытие карточки показывает агрегированные сведения о группе.
Нажатие на блок количества открывает общую табличную детализацию АСУ «Подход»
с сохранением `kpi_id` и условий KPI. Для ограничения выбранной группой
передаются `group_value` либо `group_value_is_null=Y`; API применяет поле
группировки из проверенного фиксированного шаблона. Сводные ссылки слева также
открывают эту общую таблицу, при необходимости с фильтром `cargo_state`.
В URL табличного режима используются `ctx=approach` или `ctx=departure`,
`_endpoint=/api/dislocation/detail` и `kpi_table=Y`. Отдельный упрощённый
рендерер таблицы для группы не используется.
Гружёность определяется `WagonCargoState::SQL_EXPRESSION`.

Каталог конструктора формируется методом `KpiCondition::fields()`. Поля номера
вагона, состояния вагона, веса груза, даты операции и нормативной даты доставки
в нём не показываются. `KpiCondition::compile()` продолжает поддерживать эти
поля для выполнения ранее сохранённых карточек.

Старые конфигурации `GROUPED` с `group_field=train_no` и `train_index`
поддерживаются через совместимое сопоставление в
`KpiGroupingTemplates::fromDetail()`.

Системные KPI `formed_trains` и `abandoned_trains` используют тот же компонент
карточек и обработчик раскрытия, что и пользовательский `GROUPED`. Профиль
`formed` в `ApiController::dislDetail()` группируется только по `TRAIN_NO`, а
профиль `abandoned` — только по `TRAIN_INDEX`. Дополнительные поля выбираются
через `MIN()` вместе с `COUNT(DISTINCT ...)`: при нескольких значениях карточка
показывает «Несколько значений». Для `abandoned` независимые счётчики гружёных и
порожних вагонов рассчитываются через `WagonCargoState::SQL_EXPRESSION`.
Нажатие на счётчик открывает стандартную табличную детализацию с фильтром группы
и, для счётчиков гружёности, `cargo_state`. Условия отбора KPI не изменены.
Изменения схемы Oracle не требуются; реальную выборку следует проверить на
целевой БД.

### Системные KPI прибытия и отправления по суткам

Карточки создаются повторно запускаемым скриптом
`db/kpi/2026-11-06-arrival-departure-day-kpi.sql`. Все четыре карточки имеют
`IS_SYSTEM = 'Y'`, единицу измерения `шт.`, активны после первого создания и
открывают стандартную табличную детализацию. Специальная запись в
`XX_RJD_KPI_DETAIL_CFG` для них не создаётся.

Условия находятся в
`db/XX_RJD_DISLOCATION_NEW_PKG.pkb`, функция
`XX_RJD_DISLOCATION_NEW_PKG.GET_KPI_WHERE`. Граница суток рассчитывается в
часовом поясе `Europe/Moscow`, независимо от часового пояса сервера Oracle.
`SET_KPI_LABEL` считает подходящие строки через `COUNT(*)` по последней
загруженной справке соответствующего типа и применяет общее исключение вагонов
из `XX_DISL_IDLE_CONTROL_V`.

- `arrived-today`, «Прибыло сегодня», страница «Подход вагонов»: только строки
  `TYPE_REFERENCE = 'Подход'`, станция назначения `DEST_STATION` —
  Углеуральская. Фактическая дата берётся из `ASOUP_ARRIVE_DT`, а при её
  отсутствии — из `TRIP_END_DT`; дата равна текущей московской дате.
- `arrived-yesterday`, «Прибыло вчера»: те же источник и проверка станции,
  фактическая дата равна предыдущей московской дате.
- `departed-today`, «Отправлено сегодня», страница «Отправление вагонов»:
  только строки `TYPE_REFERENCE = 'Отправка'`, `ASOUP_DEPART_DT` заполнена,
  `DEPART_STATION` — Углеуральская, дата отправления равна текущей московской
  дате.
- `departed-yesterday`, «Отправлено вчера»: те же источник и проверка станции,
  дата отправления равна предыдущей московской дате.

Карточка `arrived-yesterday` сохранена в системном справочнике, но по умолчанию
отключена через `IS_ACTIVE = 'N'`. Изменение подготовлено в
`db/kpi/2026-11-09-disable-arrived-yesterday.sql`; `SUPER` может снова включить
карточку на странице `/admin/kpi`. SQL в целевой БД применяется отдельно.

Проверка станции в package выполняется единым условием
`UPPER(TRIM(...)) LIKE '%УГЛ%768207%'`: в значении должны присутствовать часть
названия и код ЕСР станции. Табличная детализация
загружается через `ApiController::dislDetail()` в
`src/Controllers/ApiController.php`: контроллер получает условие системного KPI
из `GET_KPI_WHERE` и применяет его к строкам справки. Поля и подписи дат заданы в
`src/Reports/source-columns.php` (`asoup_arrive_dt`, `trip_end_dt`,
`asoup_depart_dt`). Изменение структуры БД не требуется.

На 06.11.2026 изменения пакета и `MERGE` подготовлены в репозитории. Состояние
их применения к целевой Oracle необходимо указать после выполнения SQL.

### Системный KPI «Груженные» на странице отправления

Карточка `loaded-wagons` создаётся повторно запускаемым скриптом
`db/kpi/2026-11-09-departure-loaded-kpi.sql` с типом `departue_kpi`, страницей
`departure`, `IS_SYSTEM = 'Y'` и единицей измерения `шт.`. Карточка открывает
стандартную табличную детализацию; отдельная запись в
`XX_RJD_KPI_DETAIL_CFG` не требуется.

Условие определено в `XX_RJD_DISLOCATION_NEW_PKG.GET_KPI_WHERE`, исходник —
`db/object/package/XX_RJD_DISLOCATION_NEW_PKG.pkb`. Выбираются только строки
справки `TYPE_REFERENCE = 'Отправка'`, отправленные со станции Углеуральская.
Проверка `DEPART_STATION` выполняется по шаблону `%УГЛ%768207%`. Как и сводная
таблица отправления, KPI учитывает только вагоны
с положительным оставшимся расстоянием `DIST_REMAIN_KM > 0`. Для обычных родов
вагонов значение `CARGO_WEIGHT_KG` должно быть больше нуля. Для платформ,
включая фитинговые платформы, вес должен быть строго больше 12000 кг.
Принадлежность к платформам определяется по наличию слова `ПЛАТФОРМ` в
`WAGON_TYPE_CODE`; пустой вес считается нулевым.

Расчёт карточки выполняет `XX_RJD_DISLOCATION_NEW_PKG.SET_KPI_LABEL`, а
детализацию — `ApiController::dislDetail()`. Изменения package и `MERGE` в
целевой Oracle этим изменением не применялись.

## Множественные фильтры отчётов

Фильтры типа `select` на страницах разделов «Движение вагонов» и «Аналитика»
поддерживают выбор нескольких значений. Признак `multiple` добавляется к
описанию фильтра в `ReportConfig::all()` по группе навигации. `app.js` передаёт
выбранный массив как JSON, а `ApiController::multiValueCondition()` формирует
параметризованное условие `IN`. Новые `select`-фильтры в этих разделах получают
множественный выбор без отдельной клиентской реализации. Раскрывающийся список
содержит поиск по вариантам; поле и меню имеют увеличенную минимальную ширину.

Переход из итоговой ячейки сводной таблицы формируется функцией `totalLink()` в
`public/assets/js/app.js`. Она передаёт тот же `group_by`, что строки дорог и
станций. Для страницы «Отправление вагонов» это `dest_road,dest_station`, поэтому
общий итог и дочерние строки используют одинаковые условия детализации.
`ApiController::applyDetailFilters()` разбирает параметры полей группировки через
`multiValueCondition()`: JSON-массив `[""]`, поступающий от незаполненного
множественного фильтра, не создаёт условие, а несколько выбранных значений
формируют параметризованный `IN`.

### Фильтры колонок детализации

Стандартные подробные таблицы используют Excel-подобный фильтр для каждого
отображаемого столбца. Меню содержит поиск, множественный выбор и команды выбора
и снятия всех значений. Фильтры разных столбцов объединяются по `AND`.
Фильтрация выполняется в браузере по уже загруженным строкам и не изменяет SQL
или условия отчёта.

Встроенная детализация реализована общим виртуальным рендерером `showTable()` в
`public/assets/js/app.js`; отдельная страница `/detail` использует одноимённый
рендерер в `templates/detail.php`. В обоих случаях список значений фильтра
строится по строкам, прошедшим все остальные активные фильтры, без ограничения
по самому текущему столбцу. При применении фильтра выбранные значения, которые
перестали быть доступными с учётом остальных фильтров, удаляются из состояния.
Обе реализации используют одинаковые классы из `public/assets/css/app.css`.
Счётчик строк и массив `filtered`, используемый выгрузкой в Excel, обновляются
после применения фильтров.

### Сортировка колонок детализации

На отдельной странице `/detail` заголовки колонок виртуальной таблицы поддерживают
циклическую сортировку: первое нажатие — по возрастанию, второе — по убыванию,
третье — возврат к исходному порядку строк, полученному от API. Сортировка
выполняется в браузере по полному массиву `_vtAllData`, а не только по строкам,
которые в данный момент отрисованы виртуальным скроллингом. Исходный массив не
изменяется; отсортированная выборка хранится в `_vtFiltered`.

После сортировки повторно применяются активные фильтры, сохраняется их состояние,
обновляются индикатор направления и счётчик строк. Фильтрация, сортировка и
выгрузка используют один итоговый массив `_vtFiltered`. Для числовых и датированных
колонок учитывается тип из конфигурации колонок; остальные значения сравниваются
как строки с числовым режимом локального сравнения. Пустые значения помещаются в
конец списка при обоих направлениях. Доступные для сортировки поля ограничены
ключами колонок текущей конфигурации отчёта с допустимым форматом имени.

Сортировка не отправляет дополнительных запросов к Oracle и не меняет API,
условия отбора, SQL, порядок/ширину/закрепление колонок или настройки фильтров.

## Карта

`MapsController::showMaps()` загружает вагоны последней справки и передаёт их в
`templates/maps.php`. Фильтры груза, арендатора и станции приписки арендатора
работают в браузере по уже загруженным вагонам. Каждый фильтр поддерживает
несколько значений и поиск внутри списка. Между фильтрами действует пересечение:
вагон должен соответствовать одному из значений каждого заполненного фильтра.
Доступные варианты каждого селекта рассчитываются по одному снимку выбранных
фильтров с исключением самого текущего фильтра. После расчёта всех списков
выбранные значения, ставшие недоступными, удаляются одновременно; затем
обновляются селекты и их элементы управления. Фильтр состояния вагонов
(гружёные, порожние, без движения) также учитывается при расчёте вариантов.


## Управление KPI (SUPER)

Страница `/admin/kpi` доступна только системной роли `SUPER`. Право и URL
зарегистрированы в `src/Services/PageRegistry.php`, HTML и POST-маршруты
зарегистрированы в `src/routes.php`. Страница использует `KpiController`
и шаблон `templates/admin/kpi.php`.

Системные KPI (`IS_SYSTEM = 'Y'`) можно редактировать только по полям `LABEL`,
`ORDER_BY`, `TREND_PERIOD`, `TREND_UNIT` и включать/отключать через `IS_ACTIVE`.
Код, тип и условия системного KPI остаются под управлением существующего PL/SQL.
Удаление системных KPI административной страницей не предусмотрено.

Пользовательские KPI (`IS_SYSTEM = 'N'`) делятся по `VISIBILITY` на личные
(`PRIVATE`) и общие (`GLOBAL`). Общую карточку может создать, изменить,
включить, отключить или глобально удалить только `SUPER`. В административном
конструкторе область видимости проверяется сервером; переданное обычным
пользователем значение `GLOBAL` заменяется на `PRIVATE`. `OWNER_ID` остаётся
идентификатором создателя и для общих карточек.

`ApiController::kpiSummary()` возвращает активные личные карточки владельца и
активные системные и общие карточки, для которых нет строки текущего пользователя в
`XX_RJD_KPI_HIDDEN`. `ApiController::dislDetail()` повторяет ту же проверку,
поэтому скрытую системную или общую карточку нельзя открыть прямым API-запросом. Методы
`UserKpiController::hide()` и `UserKpiController::restore()` получают пользователя только из сессии,
проверяют CSRF и изменяют запись `(USER_ID, KPI_ID)`. Страница `/kpi/hidden`
показывает только активные системные и общие карточки и позволяет вернуть их.
Личные KPI этим механизмом не скрываются.

Структура `VISIBILITY` и `XX_RJD_KPI_HIDDEN` подготовлена в
`db/kpi/2026-11-08-global-kpi.sql`. Миграция в БД приложением не применяется;
до её ручного выполнения новый код использовать нельзя.

Поиск, тип и страница из фильтра списка KPI сохраняются в `sessionStorage` и
восстанавливаются после возврата с POST-действий включения, отключения и
сохранения.

Признак `IS_ACTIVE` добавлен миграцией
`db/kpi/2026-11-06-kpi-admin-active.sql`. Миграцию необходимо применить в Oracle
до включения страницы. API сводных KPI и детализации исключает отключённые KPI.

## Персонализация таблиц детализации

Порядок и индивидуальные ширины столбцов таблиц детализации сохраняются для
пользователя и кода отчёта через `TableLayoutService` в
`src/Services/TableLayoutService.php`. Состав и ключи колонок проверяются по
`ReportConfig`. Позиция и ширина хранятся по `COLUMN_KEY` в
`XX_RJD_TABLE_LAYOUT_COLUMNS`; допустимая сохранённая ширина — 70–800 px.
Изменение ширины выполняется перетаскиванием правой границы заголовка, двойной
щелчок сбрасывает индивидуальную ширину. Сохранение выполняется через
`ApiController::saveTableLayout()` (`POST /api/table-layout/{reportCode}`),
получение — через `ApiController::tableLayout()`. При изменении порядка
сохранённые ширины и видимость колонок сохраняются. Для добавления поля
`COLUMN_WIDTH` требуется применить SQL-скрипт
`db/2026-11-07-table-column-width.sql` в схеме `XX_ETW`; PHP-код не выполняет
миграцию автоматически.


## Системные KPI: доступ к детализации

Карточки системных KPI формируются методом `ApiController::kpiSummary()` и
открывают общий endpoint `/api/dislocation/detail` через страницу `/detail`.
Для запроса с `kpi_id` исходная страница передаётся параметром `source_page`.
В `kpiCards()` JavaScript дополнительно формирует этот параметр по фактическому
`item.type` из ответа API, чтобы переход не зависел от наличия вложенного
`detail.params` в ответе или от fallback-конфигурации карточки. Соответствие
типов задаётся в `PageRegistry::kpiSourcePage()`:

- `dashboard_kpi` — `dashboard`;
- `approach_kpi` — `approach`;
- `departue_kpi` — `departure`;
- `loading_kpi` — `loading`.

`PageRegistry::accessPages()` использует исходную страницу для проверки роли,
а `PageAvailability::disabledPageForRequest()` — для проверки глобальной
видимости. `ApiController::dislDetail()` загружает карточку по `kpi_id` и
сверяет `source_page` с её фактическим типом. Для личных KPI сохраняется
проверка владельца, а для общих — проверка отсутствия персонального скрытия.
Запрос к KPI без допустимого `source_page` или с
несоответствием типа отклоняется. Обычные запросы детализации без `kpi_id`
по-прежнему защищены правом `wagon-detail`.

## Пункты меню справочников

Вложенные пункты меню формируются из `PageRegistry::CORE` по полю
`directory_navigation`. `PageRegistry::filterNavigation()` и `PageRegistry::canShowInMenu()`
проверяют одновременно право пользователя (с учётом `legacy_permission => directories`), системные
ограничения `ADMIN`/`SUPER` и глобальную видимость страницы. Шаблон
`templates/partials/directories-sidebar.php` дополнительно скрывает весь блок,
если нет доступа к родительской странице `directories` либо не осталось
доступных дочерних пунктов. Прямые URL и API продолжают проверяться
`PageAccessMiddleware`.

## Удаление загруженной справки РЖД

На странице `/import` метод `ImportController::show()` выводит отдельную строку
для каждой комбинации организации, точного времени `REPORT_DT` и
`TYPE_REFERENCE`. Пользователям с ролью `ADMIN` или `SUPER` рядом со строкой
доступна кнопка удаления. POST-запрос `/import/delete` проверяет роль, CSRF,
формат времени и принадлежность справки текущей организации.

`ImportController::deleteReference()` вызывает только процедуру
`XX_ETW.XX_RJD_DISLOCATION_NEW_PKG.DELETE_REFERENCE`; прямое удаление из PHP не
выполняется. Процедура объявлена в
`db/object/package/XX_RJD_DISLOCATION_NEW_PKG.pks` и реализована в
`db/object/package/XX_RJD_DISLOCATION_NEW_PKG.pkb`. Она удаляет строки
`XX_DISLOCATION_RJD` по `ORGANIZATION_ID`, точному `REPORT_DT` и
`TYPE_REFERENCE`. Организация определяется внутри package функцией
`GET_ORGANIZATION_ID()` из `USERENV.CLIENT_IDENTIFIER`; эта же функция заменяет
повторяющиеся преобразования контекста в остальных процедурах package. Действие
записывается в аудит, неожиданная ошибка — в файловый журнал через `ErrorLogger`.

Изменения package в целевой Oracle этим изменением не применялись; перед
использованием удаления необходимо вручную скомпилировать spec и body.


### Автоматический запуск пользовательских рассылок

Раздел `/admin/report-mailings` содержит кнопку «Запустить по расписанию».
POST-маршрут `/admin/report-mailings/run-due` доступен только `SUPER`, проверяет
CSRF и вызывает `MailingScheduler::runDue()`. Планировщик выбирает активные
рассылки, время которых попадает в последние пять минут, с учётом ежедневного,
еженедельного или ежемесячного расписания. `MailingService::claimScheduledRun()`
атомарно отмечает запуск, чтобы параллельные процессы не запустили одну рассылку
повторно в тот же день. Итоговые статусы и результат сохраняются в журнале
запусков.

Для внешнего планировщика предусмотрен `POST /api/automation/mailings/run` с
заголовком `Authorization: Bearer ...`. Секрет хранится в настройке
`mailing_scheduler_token` (раздел «Почта и отчёты») и сравнивается через
`hash_equals()`. Токен не возвращается в HTML и не отображается после сохранения.
Изменения структуры Oracle не требуются; выполнение на целевой БД необходимо
проверить отдельно.
