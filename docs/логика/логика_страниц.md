# Пользовательские KPI — группировка и детализация

## SQL-журнал

При включённом `app_debug` все страницы и API записывают SQL в
`tmp/log/sql_debug.log`. `SqlTraceMiddleware` назначает HTTP-запросу
`request_id` и передаёт в `QueryLogger` HTTP-метод и endpoint. Каждая
запись `OracleDb::fetchAll()` и `OracleDb::execute()` содержит цепочку
PHP-методов с путями и строками исходников, SQL, bind-параметры и
время выполнения. Ошибка Oracle записывается с пометкой `ERROR` и
кодом Oracle. Завершающая запись HTTP-запроса показывает его общее
время, количество SQL и суммарное SQL-время. Необработанное
PHP-исключение добавляет в итог класс, текст, файл и строку. Пароли, токены,
идентификаторы сессий и CSRF в bind-параметрах маскируются.

В авторизованной группе маршрутов `src/routes.php` создаёт один экземпляр
`Organizations` на HTTP-запрос. `OrganizationMiddleware` синхронизирует его,
после чего тот же экземпляр передаётся контроллерам API, KPI, импорта, карты,
профиля, рассылок и нормативов. Поэтому список доступных организаций и активная
организация не читаются из БД повторно внутри одного запроса. Внешний планировщик
рассылок и `MailingRun` используют отдельный контекст: пользовательской сессии у
планировщика нет, а при формировании рассылки организация задаётся явно.

`SessionMiddleware` вызывает `SessionRegistry::touch()` при входе и затем не
чаще одного раза в 30 секунд: это одновременно обновляет время активности и
проверяет, не отозвана ли сессия. Повторная синхронизация после контроллера
выполняется только при входе, когда до обработки запроса пользователя в сессии
ещё не было. `SessionReleaseMiddleware` закрывает запись PHP-сессии перед
обработкой защищённых `GET`/`HEAD` API. Значения `$_SESSION` остаются доступны
для чтения, а параллельные запросы больше не ожидают завершения друг друга.
Списки организаций и прав кешируются в пользовательской сессии на 60 секунд,
глобальная видимость страниц — на 30 секунд. `DbFactory` одним PL/SQL-блоком
устанавливает пользователя и организацию Oracle.

При первом открытии страницы `switchTab()` один раз вызывает `initTab()` для
активной вкладки и возвращает её AJAX-запрос. Для любого отчёта, у которого в
`ReportConfig` одновременно определены endpoint фильтров и endpoint сводной или
детальной таблицы, автоматически создаётся `/api/{report}/initial`.
`ApiController::reportInitial()` возвращает фильтры и данные одним ответом в
формате `{filters, data}`. Самостоятельный endpoint фильтров сохраняется для
повторной загрузки и страниц, которым до получения данных требуется ввод
обязательного параметра. Оверлей ожидает запрос начальных данных.
`ApiController::getReportDt()` кеширует найденный максимум по типу справки, а
`ApiController::getLatestDtsByType()` — набор последних дат по запрошенным типам
до завершения текущего HTTP-запроса. Поэтому фильтры и таблица внутри `/initial`
не запрашивают одинаковые последние даты повторно. Фильтры «Общей дислокации»
возвращают только используемый страницей список грузов; история дат справок в
этом endpoint не формируется.
Карточки KPI загружаются лениво из `switchTab()`: `dashboard_kpi` — для
«Общей дислокации», `approach_kpi` — для «Подхода», `departue_kpi` — для
«Отправления», `loading_kpi` — для «Погрузки». Все системные и доступные
пользовательские карточки выбранной
страницы рассчитываются одним вызовом пакетной функции
`XX_RJD_DISLOCATION_NEW_PKG.GET_PAGE_KPI`.
KPI других страниц до их
первого открытия не запрашиваются. Повторное открытие страницы не пересчитывает
её KPI; для «Погрузки» карточки принудительно обновляются после применения или
сброса фильтров.
Доступ к `/api/kpi/summary` определяется параметром `kpi_type` через
`PageRegistry::kpiSourcePage()`: карточки требуют право на страницу, где они
размещены, а не отдельное право `dashboard`. Глобальное отключение страницы
проверяется по тому же соответствию. При технической ошибке блок карточек
показывает безопасное сообщение и код `ERR-...` из ответа API.
Клиент вместе с `kpi_type` передаёт `source_page`. `ApiController::kpiSummary()`
до обращения к БД проверяет их соответствие через `KpiTypeRegistry`; запрос
карточек другой страницы отклоняется и не запускает расчёт KPI.

На странице «Общая дислокация» дата актуальной справки не зависит от наличия
KPI. `ApiController::dislSummary()` возвращает `updated_at` вместе со сводной,
а `loadSummary()` в `public/assets/js/app.js` обновляет дату в шапке из ответа
основного отчёта. Если для страницы не создано ни одной карточки KPI, сводная и
дата последней справки продолжают отображаться.
Единым источником последних дат справок служит pipelined-функция
`XX_RJD_DISLOCATION_NEW_PKG.GET_LATEST_REPORTS()` из
`db/XX_RJD_DISLOCATION_NEW_PKG.pkb`. Она принимает два типа справки и
необязательный календарный день. Организация берётся из
`GET_ORGANIZATION_ID()`. Для каждого типа выполняется отдельный
`MAX(REPORT_DT)`, что позволяет Oracle использовать `INDEX RANGE SCAN
(MIN/MAX)` по `IX_XX_DISL_ORG_TYPE_DT`. Типы без строк не возвращаются.
`ReportService::getLatestDtsByType()` из `src/Services/ReportService.php` читает эту
функцию через `TABLE()`; более двух типов обрабатываются парами через
`UNION ALL`. `SET_KPI_LABEL()` использует ту же функцию для текущих
данных и для последних справок за переданные сутки. Изменения package
подготовлены, но в Oracle не компилировались.

## Загрузка и скачивание справок РЖД

Для разового восстановления справок из почты используются два ручных CLI-скрипта.
`tools/download_rjd_mail.py` подключается к Microsoft Exchange через EWS, ищет
письма от `cargolk@gvc.rzd.ru` и сохраняет XLSX-вложения в `tmp/mf/rjd`.
Период задаётся параметрами `--today`, `--hours N`, `--days N` или `--months N`;
`--hours N` отсчитывает точное количество часов от момента запуска, без параметров
берутся последние два месяца. Скрипт предназначен для разового локального запуска;
параметры почтового ящика заданы непосредственно в нём.
`tools/import_rjd_directory.php` отдельно проходит по XLSX этого каталога и
вызывает публичный `ImportController::importLocalFile()`, поэтому применяются те
же проверки, архивирование и правила сохранения текущей справки, что при ручной
загрузке. После успешного `importLocalFile()` исходный XLSX удаляется; при ошибке загрузки
или удаления файл остаётся в каталоге, а скрипт завершается с кодом ошибки. Организация задаётся
переменной `RJD_ORGANIZATION_ID`, по умолчанию 1.
Числовые даты Excel в `ImportController::parseExcelDate()` преобразуются через
`Date::excelToDateTimeObject()` и сохраняются как записаны в XLSX, без перевода в
часовой пояс PHP. Одноразовое исправление ранее загруженных дат подготовлено в
`db/2026-11 new/2026-11-13-fix-imported-date-offset.sql`; скрипт уменьшает 16 полей даты на 5 часов
в текущей и архивной таблицах, но не изменяет `REPORT_DT`. SQL одноразовый и в целевой Oracle
ещё не применялся.

После загрузки текущего снимка вызывается публичная процедура
`XX_RJD_DISLOCATION_NEW_PKG.ARCHIVE_RJD_MOVEMENT`. `ImportController::importLocalFile()`
вызывает её в той же транзакции перед `COMMIT`; `PARSE_RJD_EXCEL` вызывает её
после разбора XML. Процедура обрабатывает строки всех типов
справок, включая `Отправка` и `Подход`. Первое
состояние вагона полностью копируется из `XX_DISLOCATION_RJD` в
`XX_RJD_DISLOCATION_ARCHIVE`. Архивная таблица имеет те же поля, что и основная.
Последующее
состояние добавляется только при изменении номера накладной, операции,
мнемокода операции, даты операции, станции операции, номера поезда или
индекса поезда. Перед вставкой package ищет такое же состояние во всей истории
той же организации, типа справки и вагона. Ранее уже сохранённое состояние повторно
не добавляется, даже если вагон позже переходил в другое состояние. Проверка
выполняется отдельно перед каждой вставкой под блокировкой архивной таблицы,
поэтому одинаковые строки внутри одной справки также не дублируются. Пустые
значения считаются равными, а пробелы по краям строковых полей не учитываются.
`REPORT_DT` копируется вместе с остальными
полями и не участвует в решении о добавлении нового состояния.
Таблица создаётся скриптом
`db/2026-11 new/2026-11-09-dislocation-archive.sql` как пустая копия структуры
`XX_DISLOCATION_RJD`. Скрипт сразу копирует в архив последний уже загруженный
снимок каждого типа справки и каждой организации. При последующем добавлении или изменении колонок обе
таблицы нужно менять одновременно, так как package копирует полную строку.
Повторно запускаемый скрипт
`db/2026-11 new/2026-11-10-dislocation-archive-backfill.sql` обходит все
сохранённые строки всех типов справок в `XX_DISLOCATION_RJD` от ранних к поздним и
добавляет в архив только отсутствующие состояния по тому же ключу, что и
`ARCHIVE_RJD_MOVEMENT`. Существующие архивные строки он не изменяет и не
удаляет. Скрипт подготовлен, но в целевой Oracle не применялся.
Перед вставкой новой справки дата сравнивается с максимальным `REPORT_DT` той же
организации, типа справки и календарного дня. Справка с равной или более поздней
датой заменяет дневной снимок в `XX_DISLOCATION_RJD`. Более старая справка
временно загружается в той же транзакции, дополняет архив новыми состояниями и
затем удаляется из основной таблицы. Поэтому ручная загрузка старого файла и
`PARSE_RJD_EXCEL` не откатывают текущий снимок, но позволяют восстановить
пропущенные движения. Основная таблица сохраняет снимок с максимальным
`REPORT_DT` каждого типа за каждый день.
Изменение схемы и package подготовлено, но в целевой Oracle не применялось.

Вкладка «Движение» карточки вагона загружается методом
`WagonMovement::rows()` из `src/Services/WagonMovement.php`. Параметры текущего
рейса берутся из последней актуальной справки. К существующим операциям из
`XX_DISLOCATION_RJD` добавляются строки `XX_RJD_DISLOCATION_ARCHIVE` той же
организации, с теми же номером вагона и номером накладной, для которых
`TRUNC(OPER_DT) >= TRUNC(TRIP_START_DT)` текущего рейса. Тип справки и станция
назначения архивную выборку не ограничивают. Если дата начала рейса или номер
накладной отсутствуют, архив не подключается. После объединения одинаковые
операции сворачиваются по дате, названию или мнемокоду операции и станции.
Метод принимает номер страницы и возвращает по 50 операций. Общее количество
рассчитывается после сворачивания дублей, поэтому счётчик и число страниц
соответствуют строкам, показанным пользователю. API `ApiController::wagonMovement()`
принимает параметр `page`, а `public/assets/js/wagon.js` выводит под таблицей
диапазон строк и пагинацию в общем стиле списков проекта.

Вкладка «Анализ за период» получает список грузов методом
`ApiController::analysisFilters()` и строки таблицы методом
`ApiController::analysisPeriod()` из `src/Controllers/ApiController.php`. Оба
запроса читают `XX_RJD_DISLOCATION_ARCHIVE`. Фильтры организации, номера вагона,
периода по `OPER_DT` и груза применяются к архивным строкам; основная таблица
`XX_DISLOCATION_RJD` в этой вкладке не используется. Полнота результата зависит
от выполненной дозагрузки старых данных в архив.

На странице `/import` каждая загруженная справка скачивается через
`ImportController::downloadReference()`. Метод проверяет организацию, тип и дату,
читает порядок исходных колонок из `ReportConfig::sourceColumns()` и передаёт
строки в `ExcelExport::downloadReference()`. XLSX использует оформление
`ExcelStyle::applyReferenceTable()`, применяемое также для справок в рассылках.
Перед формированием применяется лимит памяти `report_mail_memory_limit` из
`ConfigSchema` — тот же, что используется планировщиком рассылок. Это необходимо
из-за большого числа ячеек полной справки. Предварительный расчёт формул XLSX
отключён.
Кнопка скачивания в `templates/import.php` получает файл через `fetch` и на всё
время формирования показывает статус «Формируется справка…». Пока запрос не
завершён, остальные кнопки скачивания заблокированы. После получения XLSX
браузер запускает сохранение файла и снова разрешает скачивание; это исключает
повторные параллельные запросы от одного пользователя.
Удаление остаётся доступно только `ADMIN` и `SUPER`, скачивание — всем
пользователям с доступом к странице загрузки. Для скачивания изменения БД не требуются.

## Простои вагонов

`ApiController::downtimeFrom()` рассчитывает фактический простой на станции как
`station_idle_days`, но название диапазона и его порядок получает только через
`XX_RJD_DISLOCATION_NEW_PKG.FNC_GET_DOWNTIME_WAGON()`. Границы диапазонов в PHP
не дублируются. Функция пакета отдельно относит `NULL` к группе «Недостаточно
данных о начале простоя» с порядком `70`; остальные группы получают порядки
`10…60`. Изменение исходника пакета подготовлено, но в БД не применено.

Пользовательские KPI сохраняют условия в `XX_ETW.XX_RJD_KPI_TBL.WHERE_CONFIG`.
Для `TABLE` открывается стандартная детализация. Для группировки доступны только
фиксированные шаблоны `TRAIN_NUMBER` (по номеру поезда) и `TRAIN_INDEX`
(по индексу поезда). Их определения находятся в
`src/Reports/Kpi/KpiGroupingTemplates.php`; в Oracle сохраняется только код шаблона
в `WHERE_CONFIG.detail.template`.

`ApiController::dislDetail()` применяет условия KPI, группирует вагоны по полю,
заданному шаблоном, и возвращает сводные показатели, маршрут и фиксированные
поля группы. Карточка KPI, её условие и активная конфигурация детализации
читаются одним запросом. Итоги по всем группам рассчитываются аналитическими
суммами в запросе группировки, без повторного чтения того же набора вагонов.
Для специальной группировки `templates/detail.php` не запрашивает настройки
колонок обычной таблицы. Раскрытие карточки показывает агрегированные сведения о группе.
Нажатие на блок количества открывает общую табличную детализацию АСУ «Подход»
с сохранением `kpi_id` и условий KPI. Для ограничения выбранной группой
передаются `group_value` либо `group_value_is_null=Y`; API применяет поле
группировки из проверенного фиксированного шаблона. Сводные ссылки слева также
открывают эту общую таблицу, при необходимости с фильтром `cargo_state`.
В URL табличного режима используются `ctx=approach` или `ctx=departure`,
`_endpoint=/api/dislocation/detail` и `kpi_table=Y`. Отдельный упрощённый
рендерер таблицы для группы не используется.
Гружёность определяет функция
`XX_RJD_DISLOCATION_NEW_PKG.FNC_GET_CARGO_STATE()` из
`db/XX_RJD_DISLOCATION_NEW_PKG.pkb`: для платформ и фитинговых платформ вагон
считается гружёным при весе больше 12000 кг, для остальных родов — при весе
больше нуля. `WagonCargoState::SQL_EXPRESSION` содержит только вызов этой
функции и не повторяет порог в PHP. Карта также получает рассчитанный признак
из Oracle.

На карточке созданного пользователем KPI доступны редактирование и персональное
скрытие. Удаление находится только в форме редактирования и требует отдельного
подтверждения. Скрытые личные KPI отображаются в общем окне «Скрытые KPI» и
могут быть возвращены тем же способом, что системные и общие карточки. Создание
и редактирование открывают одну форму в модальном окне; сохранение, удаление и
отмена закрывают его без перехода на отдельную страницу.

Каталог конструктора формируется методом `KpiCondition::fields()`. Поля номера
вагона, состояния вагона, веса груза, даты операции и нормативной даты доставки
в нём не показываются. `KpiCondition::compile()` продолжает поддерживать эти
поля для выполнения ранее сохранённых карточек.
Список типов KPI, соответствующие страницы, подписи, контейнеры, типы справок и
поля конструктора определены в `src/Reports/Kpi/KpiTypeRegistry.php`.
В конструкторах страниц «Подход вагонов» и «Отправление вагонов» доступны
условия по грузоотправителю (`CONSIGNOR`) и грузополучателю (`CONSIGNEE`).
`KpiCondition`, `PageRegistry`, `UserKpiController`, `ApiController`, формы и
JavaScript не содержат отдельных списков типов. Клиент получает безопасную
часть реестра через `window.APP_KPI_TYPES`. Сейчас пользовательское создание
разрешено для `approach_kpi` и исторически названного `departue_kpi`.
Настройка `user_kpi_management_enabled` из `ConfigSchema` управляет созданием,
редактированием, скрытием и восстановлением KPI. При значении `false` кнопки и
диалоги не выводятся, а прямые WEB-маршруты возвращают 404 и API/POST-действия —
403. Уже созданные пользовательские и системные KPI продолжают отображаться и
рассчитываться. Управление параметрами системных KPI на странице администратора
остаётся доступным. Значение по умолчанию — `false`.
Условия в карточке можно объединить через `AND` (должны выполняться все условия)
или `OR` (достаточно любого условия). Выбранный оператор сохраняется в
`XX_RJD_KPI_TBL.WHERE_CONFIG.operator` и проверяется методом `KpiCondition::compile()`.

Старые конфигурации `GROUPED` с `group_field=train_no` и `train_index`
поддерживаются через совместимое сопоставление в
`KpiGroupingTemplates::fromDetail()`.

Системные KPI `formed_trains`, `abandoned_trains` и `abandoned_wagons`
используют тот же компонент
карточек и обработчик раскрытия, что и пользовательский `GROUPED`. Профиль
`formed` в `ApiController::dislDetail()` группируется только по `TRAIN_NO`, а
профиль `abandoned` — только по `TRAIN_INDEX`. Значение KPI
`Брошенные поезда` для обоих кодов `abandoned_trains` и `abandoned_wagons`
рассчитывается в `XX_RJD_DISLOCATION_NEW_PKG.GET_PAGE_KPI()`
и `XX_RJD_DISLOCATION_NEW_PKG.SET_KPI_LABEL()` как
`COUNT(DISTINCT TRIM(TRAIN_INDEX))` по строкам, прошедшим условия KPI;
пустой `TRAIN_INDEX` не учитывается. Для группировки по номеру поезда
`ApiController::addTrainIndexGroups()` дополнительно группирует вагоны по
`TRAIN_INDEX`. Если у номера поезда несколько индексов, раскрытая карточка
показывает вложенные группы индексов с количеством вагонов. Каждая группа
сразу раскрыта, её можно свернуть отдельно; внутри показываются агрегированные
сведения только своего индекса. При единственном индексе лишний уровень не
выводится. Для `OPER_DT` и `TRIP_START_DT` запрос всегда возвращает минимальную
дату внутри группы через `MIN()`; счётчик разных значений для этих полей не
рассчитывается. Остальные поля
выбираются через `MIN()` вместе с `COUNT(DISTINCT ...)`. Для `abandoned`
независимые счётчики гружёных и
порожних вагонов рассчитываются через `WagonCargoState::SQL_EXPRESSION`, то
есть через `XX_RJD_DISLOCATION_NEW_PKG.FNC_GET_CARGO_STATE()`.
В профиле `formed` сводные показатели карточки по номеру поезда показывают
отдельно количество гружёных и порожних вагонов; общий показатель «Вагоны»
не выводится. Оба значения открывают табличную детализацию с соответствующим
фильтром `cargo_state`.
Нажатие на счётчик открывает стандартную табличную детализацию с фильтром группы
и, для счётчиков гружёности, `cargo_state`. Условия отбора KPI не изменены. Для профиля `abandoned` на том же экране детализации доступны фильтры по источнику (`Подход`/`Отправка`), станции операции, минимальному простою в сутках и тексту поиска по индексу, номеру поезда или номеру вагона. В карточке выводятся дата операции (`OPER_DT`), дата получения данных (`REPORT_DT`) и продолжительность простоя из поля `IDLE_TIME_HHMMSS`. Источник используется как условие отбора.
В детализациях «По номеру поезда» (`TRAIN_NUMBER`) и «По индексу поезда»
(`TRAIN_INDEX`) пользователю с правом `maps` в левой колонке под заголовком
«Итоги» доступна кнопка с цветной иконкой маршрута и подсказкой «Показать на карте».
`templates/detail.php` передаёт странице `/maps` параметры текущей детализации,
а `templates/maps.php` получает номера вагонов через тот же метод
`ApiController::dislDetail()` (`/api/dislocation/detail`) и оставляет на карте
только найденные вагоны. Отдельная копия SQL-условий KPI для карты не создаётся.
Для строк с операционной станцией, содержащей `УГЛЕУРАЛ`, признак гружёности
рассчитывается через `XX_RJD_DISLOCATION_NEW_PKG.FNC_GET_PN_CARGO_STATE`
по данным внутренней дислокации ПН (`XX_ETW.XX_DISL_ROUND` и связанных
таблиц). При отсутствии веса возвращается `неопр.`; для остальных станций
сохраняется расчёт `FNC_GET_CARGO_STATE` по весу из справки РЖД.
В package добавлены функции `FNC_GET_CARGO_STATE` и `FNC_GET_PN_CARGO_STATE`;
изменения package в целевой
Oracle не применялись. До проверки страниц необходимо вручную скомпилировать
`db/XX_RJD_DISLOCATION_NEW_PKG.pks` и
`db/XX_RJD_DISLOCATION_NEW_PKG.pkb`.

### Системные KPI прибытия и отправления по суткам

Карточки создаются повторно запускаемым скриптом
`db/kpi/2026-11-06-arrival-departure-day-kpi.sql`. Все четыре карточки имеют
`IS_SYSTEM = 'Y'`, единицу измерения `шт.`, активны после первого создания и
открывают стандартную табличную детализацию. Специальная запись в
`XX_RJD_KPI_DETAIL_CFG` для них не создаётся.

Условия находятся в
`db/XX_RJD_DISLOCATION_NEW_PKG.pkb`, функция
`XX_RJD_DISLOCATION_NEW_PKG.GET_KPI_WHERE`. Граница суток рассчитывается в
часовом поясе `Europe/Moscow`, независимо от часового пояса сервера Oracle.
`SET_KPI_LABEL` считает подходящие строки через `COUNT(*)` по последней
загруженной справке соответствующего типа и применяет общее исключение вагонов
из `XX_DISL_IDLE_CONTROL_V`.

- `arrived-today`, «Прибыло сегодня», страница «Подход вагонов»: только строки
  `TYPE_REFERENCE = 'Подход'`, станция назначения `DEST_STATION` —
  Углеуральская. Фактическая дата берётся из `ASOUP_ARRIVE_DT`, а при её
  отсутствии — из `TRIP_END_DT`; дата равна текущей московской дате.
- `arrived-yesterday`, «Прибыло вчера»: те же источник и проверка станции,
  фактическая дата равна предыдущей московской дате.
- `departed-today`, «Отправлено сегодня», страница «Отправление вагонов»:
  только строки `TYPE_REFERENCE = 'Отправка'`, `ASOUP_DEPART_DT` заполнена,
  `DEPART_STATION` — Углеуральская, дата отправления равна текущей московской
  дате.
- `departed-yesterday`, «Отправлено вчера»: те же источник и проверка станции,
  дата отправления равна предыдущей московской дате.

Карточка `arrived-yesterday` сохранена в системном справочнике, но по умолчанию
отключена через `IS_ACTIVE = 'N'`. Изменение подготовлено в
`db/kpi/2026-11-09-disable-arrived-yesterday.sql`; `SUPER` может снова включить
карточку на странице `/admin/kpi`. SQL в целевой БД применяется отдельно.

Проверка станции в package выполняется единым условием
`UPPER(TRIM(...)) LIKE '%УГЛ%768207%'`: в значении должны присутствовать часть
названия и код ЕСР станции. Табличная детализация
загружается через `ApiController::dislDetail()` в
`src/Controllers/ApiController.php`: контроллер получает условие системного KPI
из `GET_KPI_WHERE` и применяет его к строкам справки. Поля и подписи дат заданы в
`src/Reports/rjd-reference-columns.php` (`asoup_arrive_dt`, `trip_end_dt`,
`asoup_depart_dt`). Изменение структуры БД не требуется.

На 06.11.2026 изменения пакета и `MERGE` подготовлены в репозитории. Состояние
их применения к целевой Oracle необходимо указать после выполнения SQL.

### Системный KPI «Груженные» на странице отправления

Карточка `loaded-wagons` создаётся повторно запускаемым скриптом
`db/2026-11 old/kpi/2026-11-09-departure-loaded-kpi.sql` с типом `departue_kpi`, страницей
`departure`, `IS_SYSTEM = 'Y'` и единицей измерения `шт.`. Карточка открывает
стандартную табличную детализацию; отдельная запись в
`XX_RJD_KPI_DETAIL_CFG` не требуется.

Условие определено в `XX_RJD_DISLOCATION_NEW_PKG.GET_KPI_WHERE`, исходник —
`db/XX_RJD_DISLOCATION_NEW_PKG.pkb`. Выбираются только строки
справки `TYPE_REFERENCE = 'Отправка'`, отправленные со станции Углеуральская.
Проверка `DEPART_STATION` выполняется по шаблону `%УГЛ%768207%`. KPI учитывает только вагоны
с положительным оставшимся расстоянием `DIST_REMAIN_KM > 0`. Для обычных родов
вагонов значение `CARGO_WEIGHT_KG` должно быть больше нуля. Для платформ,
включая фитинговые платформы, вес должен быть строго больше 12000 кг.
Принадлежность к платформам определяется по наличию слова `ПЛАТФОРМ` в
`WAGON_TYPE_CODE`; пустой вес считается нулевым. Само правило выполняет
`FNC_GET_CARGO_STATE`, поэтому порог не повторяется в условии KPI.

Расчёт карточки выполняет `XX_RJD_DISLOCATION_NEW_PKG.SET_KPI_LABEL`, а
детализацию — `ApiController::dislDetail()`. Изменения package и `MERGE` в
целевой Oracle этим изменением не применялись.

## Множественные фильтры отчётов

Фильтры типа `select` на всех страницах отчётов поддерживают выбор нескольких
значений. Признак `multiple` добавляется к описанию каждого такого фильтра в
`ReportConfig::all()` независимо от раздела меню. `app.js` передаёт выбранный
массив как JSON, а сервер формирует параметризованное условие `IN`. Основные
отчёты используют `ApiController::multiValueCondition()`, на странице
«Претензии» массивы станций и родов вагонов разбирает `Claims::filterValues()`.
Новые `select`-фильтры получают множественный выбор без отдельной клиентской
реализации. Раскрывающийся список содержит поиск по вариантам; поле и меню имеют
увеличенную минимальную ширину. На странице «Сырьё» сейчас нет фильтра типа
`select`, поэтому её единственное поле «№ вагона» остаётся текстовым.

Переход из итоговой ячейки сводной таблицы формируется функцией `totalLink()` в
`public/assets/js/app.js`. Она передаёт тот же `group_by`, что строки дорог и
станций. Для страницы «Отправление вагонов» это `dest_road,dest_station`, поэтому
общий итог и дочерние строки используют одинаковые условия детализации.
`ApiController::applyDetailFilters()` разбирает параметры полей группировки через
`multiValueCondition()`: JSON-массив `[""]`, поступающий от незаполненного
множественного фильтра, не создаёт условие, а несколько выбранных значений
формируют параметризованный `IN`.

Кнопка «Назад» в `templates/detail.php` учитывает цепочку детализаций. Если
текущая детализация открыта переходом с другой страницы `/detail`, выполняется
`history.back()` и пользователь возвращается на предыдущий уровень. Первая
детализация, открытая из основной страницы в новой вкладке, по кнопке закрывает
эту вкладку, как и раньше.

### Фильтры колонок детализации

Стандартные подробные таблицы используют Excel-подобный фильтр для каждого
отображаемого столбца. Меню содержит поиск, множественный выбор и команды выбора
и снятия всех значений. Фильтры разных столбцов объединяются по `AND`.
Фильтрация выполняется в браузере по уже загруженным строкам и не изменяет SQL
или условия отчёта.

Встроенная детализация реализована общим виртуальным рендерером `showTable()` в
`public/assets/js/app.js`; отдельная страница `/detail` использует одноимённый
рендерер в `templates/detail.php`. В обоих случаях список значений фильтра
строится по строкам, прошедшим все остальные активные фильтры, без ограничения
по самому текущему столбцу. При применении фильтра выбранные значения, которые
перестали быть доступными с учётом остальных фильтров, удаляются из состояния.
Обе реализации используют одинаковые классы из `public/assets/css/app.css`.
Счётчик строк и массив `filtered`, используемый выгрузкой в Excel, обновляются
после применения фильтров.

### Сортировка колонок детализации

На отдельной странице `/detail` заголовки колонок виртуальной таблицы поддерживают
циклическую сортировку: первое нажатие — по возрастанию, второе — по убыванию,
третье — возврат к исходному порядку строк, полученному от API. Сортировка
выполняется в браузере по полному массиву `_vtAllData`, а не только по строкам,
которые в данный момент отрисованы виртуальным скроллингом. Исходный массив не
изменяется; отсортированная выборка хранится в `_vtFiltered`.

После сортировки повторно применяются активные фильтры, сохраняется их состояние,
обновляются индикатор направления и счётчик строк. Фильтрация, сортировка и
выгрузка используют один итоговый массив `_vtFiltered`. Для числовых и датированных
колонок учитывается тип из конфигурации колонок; остальные значения сравниваются
как строки с числовым режимом локального сравнения. Пустые значения помещаются в
конец списка при обоих направлениях. Доступные для сортировки поля ограничены
ключами колонок текущей конфигурации отчёта с допустимым форматом имени.

Сортировка не отправляет дополнительных запросов к Oracle и не меняет API,
условия отбора, SQL, порядок/ширину/закрепление колонок или настройки фильтров.

## Карта

`MapsController::showMaps()` загружает вагоны последней справки и передаёт их в
`templates/maps.php`. Фильтры груза, арендатора и станции приписки арендатора
работают в браузере по уже загруженным вагонам. Каждый фильтр поддерживает
несколько значений и поиск внутри списка. Между фильтрами действует пересечение:
вагон должен соответствовать одному из значений каждого заполненного фильтра.
Доступные варианты каждого селекта рассчитываются по одному снимку выбранных
фильтров с исключением самого текущего фильтра. После расчёта всех списков
выбранные значения, ставшие недоступными, удаляются одновременно; затем
обновляются селекты и их элементы управления. Фильтр состояния вагонов
(гружёные, порожние, без движения) также учитывается при расчёте вариантов.

Номер вагона в списке станции открывает карточку `/wagon` с параметром
`wagon_no`. Карточку формирует `DashboardController::wagon()`. Ссылка выводится
только пользователю с правом `wagon-card`; это же право отдельно защищает маршрут
карточки на сервере.


## Управление KPI (SUPER)

### Пользовательские KPI простоев

Тип `downtime_kpi` размещается на странице «Простои» в контейнере
`data-kpi-container="downtime_kpi"`. `ApiController::userKpiSummary()` не вызывает
`GET_PAGE_KPI()`: для каждой доступной личной или GLOBAL карточки он применяет
`KpiCondition::compile()` к источнику `downtimeFrom([])`. Источник объединяет
последние справки «Подход» и «Отправка», добавляет организационное ограничение и
не получает фильтры текущей страницы (станцию, вагон, порог и представление).
Карточка возвращает количество вагонов и агрегаты простоя; детализация через
`ApiController::dislDetail()` использует тот же источник и сохранённые условия.
Шаблон `WAGON_TYPE` из `KpiGroupingTemplates` группирует по `wagon_type_code` и
показывает продолжительность, количество гружёных и порожних вагонов.
Для всех группируемых KPI при наличии права `maps` в блоке «Итоги» отображается
кнопка карты; для `WAGON_TYPE` она открывает вагоны всей карточки. В каждой строке
группы отдельно выводятся общее количество, гружёные и порожние вагоны, а их
счётчики открывают дополнительную табличную детализацию с сохранением группы и
состояния груза.
Для сохранения таких карточек в Oracle ограничение
`XX_RJD_KPI_TBL_PAGE_CK` должно разрешать `PAGE_CODE = 'downtime'`; DDL для этого
находится в `db/kpi/2026-11-13-allow-downtime-user-kpi.sql` и в целевой БД ещё не
применялся. Полный текущий список страниц пользовательских KPI: `approach`,
`departure`, `downtime`; он совпадает с типами `approach_kpi`, `departue_kpi` и
`downtime_kpi` в `KpiTypeRegistry`. Остальные страницы намеренно не включены,
поскольку создание пользовательских KPI для них отключено.

Страница `/admin/kpi` доступна только системной роли `SUPER`. Право и URL
зарегистрированы в `src/Services/PageRegistry.php`, HTML и POST-маршруты
зарегистрированы в `src/routes.php`. Страница использует `KpiController`
и шаблон `templates/admin/kpi.php`.

Системные KPI (`IS_SYSTEM = 'Y'`) можно редактировать только по полям `LABEL`,
`ORDER_BY`, `TREND_PERIOD`, `TREND_UNIT` и включать/отключать через `IS_ACTIVE`.
Код, тип и условия системного KPI остаются под управлением существующего PL/SQL.
Удаление системных KPI административной страницей не предусмотрено.

Пользовательские KPI (`IS_SYSTEM = 'N'`) делятся по `VISIBILITY` на личные
(`PRIVATE`) и общие (`GLOBAL`). Общую карточку может создать, изменить,
включить, отключить или глобально удалить только `SUPER`. В административном
конструкторе область видимости проверяется сервером; переданное обычным
пользователем значение `GLOBAL` заменяется на `PRIVATE`. `OWNER_ID` остаётся
идентификатором создателя и для общих карточек.

`ApiController::kpiSummary()` возвращает активные личные карточки владельца и
активные системные и общие карточки, для которых нет строки текущего пользователя в
`XX_RJD_KPI_HIDDEN`. `ApiController::dislDetail()` повторяет ту же проверку,
поэтому скрытую системную или общую карточку нельзя открыть прямым API-запросом. Методы
`UserKpiController::hide()` и `UserKpiController::restore()` получают пользователя только из сессии,
проверяют CSRF и изменяют запись `(USER_ID, KPI_ID)`. Страница `/kpi/hidden`
показывает только активные системные и общие карточки и позволяет вернуть их.
Личные KPI этим механизмом не скрываются.

Структура `VISIBILITY` и `XX_RJD_KPI_HIDDEN` подготовлена в
`db/kpi/2026-11-08-global-kpi.sql`. Миграция в БД приложением не применяется;
до её ручного выполнения новый код использовать нельзя.

Поиск, тип и страница из фильтра списка KPI сохраняются в `sessionStorage` и
восстанавливаются после возврата с POST-действий включения, отключения и
сохранения.

Признак `IS_ACTIVE` добавлен миграцией
`db/kpi/2026-11-06-kpi-admin-active.sql`. Миграцию необходимо применить в Oracle
до включения страницы. API сводных KPI и детализации исключает отключённые KPI.

## Персонализация таблиц детализации

Порядок и индивидуальные ширины столбцов таблиц детализации сохраняются для
пользователя и кода отчёта через `TableLayoutService` в
`src/Services/TableLayoutService.php`. Состав и ключи колонок проверяются по
`ReportConfig`. Позиция и ширина хранятся по `COLUMN_KEY` в
`XX_RJD_TABLE_LAYOUT_COLUMNS`; допустимая сохранённая ширина — 70–800 px.
Изменение ширины выполняется перетаскиванием правой границы заголовка, двойной
щелчок сбрасывает индивидуальную ширину. Сохранение выполняется через
`ApiController::saveTableLayout()` (`POST /api/table-layout/{reportCode}`),
получение — через `ApiController::tableLayout()`. При изменении порядка
сохранённые ширины и видимость колонок сохраняются. Для добавления поля
`COLUMN_WIDTH` требуется применить SQL-скрипт
`db/2026-11-07-table-column-width.sql` в схеме `XX_ETW`; PHP-код не выполняет
миграцию автоматически.


## KPI: расчёт и доступ к детализации

Весь блок KPI формируется методом `ApiController::kpiSummary()` и
одним запросом читаются из pipelined-функции
`XX_RJD_DISLOCATION_NEW_PKG.GET_PAGE_KPI(p_kpi_type, p_user_id)`. Функция
выбирает активные нескрытые системные, личные и общие карточки только
переданного типа и рассчитывает их
текущие значения одной условной агрегацией по актуальным справкам. Тип страницы
проверяется через `KpiTypeRegistry`; организация определяется package из
Oracle-контекста. Сохранённые JSON-условия пользовательских KPI проверяются и
преобразуются в SQL функцией `GET_USER_KPI_WHERE()`. Для совместимости с Oracle 11g
строковые значения JSON читаются внутренней PL/SQL-функцией `GET_JSON_TEXT()` без `JSON_TABLE`
и других SQL/JSON-функций. Поля и операторы ограничены тем же
набором, что и `KpiCondition::compile()` при сохранении. Вместе со значениями package возвращает дату справки
строкой в формате `DD.MM.YYYY HH24:MI`,
владельца, видимость, JSON карточки и настройки детализации. Поэтому `ApiController::kpiSummary()` не
выполняет дополнительные SQL-запросы для блока KPI.
Источник агрегации ограничивается до расчёта карточек: `approach_kpi` читает
только максимальную справку «Подход», `departue_kpi` и `loading_kpi` — только
максимальную «Отправка», `dashboard_kpi` — обе максимальные справки. Максимумы
заданы скалярными подзапросами по `organization_id`, `type_reference` и
`report_dt`, чтобы использовать индекс `IX_XX_DISL_ORG_TYPE_DT` и не соединять
основную выборку с общей pipelined-функцией последних справок.

Функция объявлена и реализована в актуальных
`db/XX_RJD_DISLOCATION_NEW_PKG.pks` и `.pkb`. Изменения package подготовлены,
но в целевой Oracle не применялись. Обычные карточки открывают общий endpoint
`/api/dislocation/detail` через страницу `/detail`; карточки погрузки передают
`loading_period` в детализацию страницы «Погрузка».
Для запроса с `kpi_id` исходная страница передаётся параметром `source_page`.
В `kpiCards()` JavaScript дополнительно формирует этот параметр по фактическому
`item.type` из ответа API, чтобы переход не зависел от наличия вложенного
`detail.params` в ответе или от fallback-конфигурации карточки. Соответствие
типов задаётся в `PageRegistry::kpiSourcePage()`:

- `dashboard_kpi` — `dashboard`;
- `approach_kpi` — `approach`;
- `departue_kpi` — `departure`;
- `loading_kpi` — `loading`.

`PageRegistry::accessPages()` использует исходную страницу для проверки роли,
а `PageAvailability::disabledPageForRequest()` — для проверки глобальной
видимости. `ApiController::dislDetail()` загружает карточку по `kpi_id` и
сверяет `source_page` с её фактическим типом. Для личных KPI сохраняется
проверка владельца, а для общих — проверка отсутствия персонального скрытия.
Запрос к KPI без допустимого `source_page` или с
несоответствием типа отклоняется. Обычные запросы детализации без `kpi_id`
по-прежнему защищены правом `wagon-detail`.

## Пункты меню справочников

Вложенные пункты меню формируются из `PageRegistry::CORE` по полю
`directory_navigation`. `PageRegistry::filterNavigation()` и `PageRegistry::canShowInMenu()`
проверяют одновременно право пользователя (с учётом `legacy_permission => directories`), системные
ограничения `ADMIN`/`SUPER` и глобальную видимость страницы. Шаблон
`templates/partials/directories-sidebar.php` дополнительно скрывает весь блок,
если нет доступа к родительской странице `directories` либо не осталось
доступных дочерних пунктов. Прямые URL и API продолжают проверяться
`PageAccessMiddleware`.

## Удаление загруженной справки РЖД

На странице `/import` метод `ImportController::show()` выводит отдельную строку
для каждой комбинации организации, точного времени `REPORT_DT` и
`TYPE_REFERENCE`. Пользователям с ролью `ADMIN` или `SUPER` рядом со строкой
доступна кнопка удаления. POST-запрос `/import/delete` проверяет роль, CSRF,
формат времени и принадлежность справки текущей организации.

`ImportController::deleteReference()` вызывает только процедуру
`XX_ETW.XX_RJD_DISLOCATION_NEW_PKG.DELETE_REFERENCE`; прямое удаление из PHP не
выполняется. Процедура объявлена в
`db/object/package/XX_RJD_DISLOCATION_NEW_PKG.pks` и реализована в
`db/object/package/XX_RJD_DISLOCATION_NEW_PKG.pkb`. Она удаляет строки
`XX_DISLOCATION_RJD` по `ORGANIZATION_ID`, точному `REPORT_DT` и
`TYPE_REFERENCE`. Организация определяется внутри package функцией
`GET_ORGANIZATION_ID()` из `USERENV.CLIENT_IDENTIFIER`; эта же функция заменяет
повторяющиеся преобразования контекста в остальных процедурах package. Действие
записывается в аудит, неожиданная ошибка — в файловый журнал через `ErrorLogger`.

Изменения package в целевой Oracle этим изменением не применялись; перед
использованием удаления необходимо вручную скомпилировать spec и body.


### Автоматический запуск пользовательских рассылок

Раздел `/admin/report-mailings` содержит кнопку «Запустить по расписанию».
POST-маршрут `/admin/report-mailings/run-due` доступен только `SUPER`, проверяет
CSRF и вызывает `MailingScheduler::runDue()`. Планировщик выбирает активные
рассылки, время которых попадает в последние пять минут, с учётом ежедневного,
еженедельного или ежемесячного расписания. `MailingService::claimScheduledRun()`
атомарно отмечает запуск, чтобы параллельные процессы не запустили одну рассылку
повторно в тот же день. Итоговые статусы и результат сохраняются в журнале
запусков.

Для внешнего планировщика предусмотрен `POST /api/automation/mailings/run` с
заголовком `Authorization: Bearer ...`. Секрет хранится в настройке
`mailing_scheduler_token` (раздел «Почта и отчёты») и сравнивается через
`hash_equals()`. Токен не возвращается в HTML и не отображается после сохранения.
Изменения структуры Oracle не требуются; выполнение на целевой БД необходимо
проверить отдельно.
## Общие исключения отчётов и KPI

Все источники справки РЖД используют общий фильтр, формируемый функцией
`XX_ETW.XX_RJD_DISLOCATION_NEW_PKG.GET_REPORT_WHERE` (`db/XX_RJD_DISLOCATION_NEW_PKG.pks/.pkb`).
Он исключает номера вагонов, начинающиеся с `0`, пустые номера и строки с
операцией «ИСКЛЮЧЕНИЕ ВАГОНА ИЗ ВАГОННОЙ МОДЕЛИ ДОРОГИ». Для страниц `approach`,
`departure`, `loading` и `raw-material` функция дополнительно возвращает условие
типа справки; `dislocation` и `downtime` используют только общую часть.

`ApiController::reportWhere()` получает этот доверенный фрагмент из Oracle и
кэширует его в рамках HTTP-запроса. Дата, организация и фильтры пользователя
добавляются отдельно bind-параметрами. `GET_PAGE_KPI`, `FNC_CHECK_KPI` и
`SET_KPI_LABEL` объединяют базовое условие страницы с условием конкретной KPI.
Пороговые значения, станции, даты и группировки остаются бизнес-условиями
конкретного отчёта или KPI. Изменение package в Oracle требует отдельной
компиляции; состояние применения к целевой базе этим изменением не подтверждается.

Для сводной страницы «Подход» `DislDataSource::approachSource()` один раз
присоединяет актуальные данные ПН и вычисляет `pn_cargo_state` по полям
`pn_car_type` и `pn_weight_net`. Повторный вызов
`FNC_GET_APPROACH_CARGO_STATE()` для каждой строки не используется. Если для
Углеуральской станции вес ПН отсутствует, состояние остаётся `неопр.`; для
остальных строк применяется `FNC_GET_CARGO_STATE()` по данным справки РЖД.
На странице «Подход вагонов» фильтр «Источник» передаёт параметр
`cargo_state_source`. Значение `pn` («Дислокация ПН») выбрано по умолчанию и
использует `pn_cargo_state`; значение `rjd` («Справка РЖД») включает прежний
расчёт `FNC_GET_CARGO_STATE()` по типу вагона и весу из справки РЖД. Выбор передаётся
в сводную, подробную таблицу и drill-down. Расчёт по данным ПН применяется только на
этой странице. Общая
дислокация и остальные отчёты используют `WagonCargoState::SQL_EXPRESSION`, то
есть `FNC_GET_CARGO_STATE()` по типу вагона и весу из справки РЖД.
Сводная матрица строит подколонки только для фактически найденных сочетаний типа
вагона и состояния груза. Например, `неопр.` выводится только внутри того типа
вагона, для которого такие строки вернул запрос; пустая подколонка у остальных
типов не создаётся. Блок «Итого» объединяет одинаковые состояния из всех типов.
Поля `pn_cargo_state` («Состояние груза») и `report_wagon_type` («Род вагона»)
также выводятся в табличной детализации и на вкладке «Подробная» страницы
«Подход вагонов». Используются уже рассчитанные значения источника без
дополнительного запроса к данным ПН и повторного расчёта колонок сводной.
Выгрузка сводной матрицы в Excel использует те же рассчитанные подколонки «Итого»,
что и экранная таблица. Закреплённая строка станции, изъятая из обычной иерархии для показа
над «Общим итогом», добавляется в Excel отдельно и не теряется.
### Варианты сводной «Простои»

В `ReportConfig` для отчёта `downtime` зарегистрированы варианты представления
строк: `cargo` (груз → интервал простоя), `idle-period` (интервал простоя) и
`destination-station` (станция назначения → груз → интервал простоя). Выбор меняет только левую
группировку. Колонки
`m_wagon_type_code` и `m_wag_state`, то есть род вагона и состояние
«гружёный/порожний», остаются одинаковыми во всех вариантах.
В представлении `destination-station` станция Углеуральская выводится первой,
остальные станции сортируются по названию.

Для отчёта добавлен числовой фильтр `Простой не менее, сут.` (`min_days`).
Он отбирает вагоны по расчётному `station_idle_days` в `ApiController::downtimeFrom()`.

`ApiController::downtimeSummary()` получает код `summary_view` и использует
только зарегистрированные в `ReportConfig` поля. Произвольные поля из запроса
не подставляются. `public/assets/js/app.js` передаёт выбранный вариант в API,
использует его группировку для перехода в детализацию и экспорта текущей
сводной.

Вариант `ugleuralskaya` («На Углеуральской») отбирает только эту станцию и группирует строки по грузу и интервалу простоя.

### Реестр страниц, отчётов и KPI

Конфигурация отчётной страницы собирается из именованных методов реестров:
`ReportConfig::<page>()` описывает только данные отчёта, а
`KpiTypeRegistry::<page>Kpi()` — источник и поля KPI. `PageRegistry` связывает
эти настройки с маршрутом, правами, навигацией и layout. Стандартные отчёты
выводятся общим шаблоном `templates/partials/wagon-report.php`; отдельный
шаблон создаётся только для уникальной разметки. Переходные массивы и отдельные шаблоны стандартных страниц не используются.
