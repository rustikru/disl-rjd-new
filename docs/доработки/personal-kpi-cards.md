# Пользовательские KPI

## Назначение

Пользовательские карточки включаются отдельно для каждого типа в
`src/Reports/KpiTypeRegistry.php`. Сейчас это «Подход вагонов» (`approach_kpi`),
«Отправление вагонов» (`departue_kpi`) и «Простои» (`downtime_kpi`). Карточки
доступны создавшему их пользователю; `SUPER` может создавать общие карточки.
Системные KPI сохраняют отдельную PL/SQL-логику.

## Хранение

Пользовательские и системные карточки находятся в `XX_ETW.XX_RJD_KPI_TBL`. Для пользовательских карточек используются `PAGE_CODE`, `OWNER_ID`, `IS_SYSTEM = 'N'`, `VISIBILITY` и `WHERE_CONFIG CLOB`. `PRIVATE` обозначает личную карточку, `GLOBAL` — общую. Условия хранятся как JSON. Системные условия остаются в `XX_ETW.XX_RJD_DISLOCATION_NEW_PKG.GET_KPI_WHERE`.

Персональное скрытие системной или общей карточки хранится одной строкой в `XX_ETW.XX_RJD_KPI_HIDDEN` с ключом `(USER_ID, KPI_ID)`. Данные карточки не копируются. Личные карточки этим механизмом не скрываются. Миграция находится в `db/kpi/2026-11-08-global-kpi.sql` и кодом приложения не выполняется.

## Условия отбора

`src/Reports/KpiCondition.php` проверяет поля и операторы и формирует SQL с bind-параметрами. Для строкового оператора «Содержит» используется `LIKE`: приложение добавляет `%` в начало и конец значения. Пользователь также может указывать `%` (любая последовательность символов) и `_` (один символ) внутри шаблона. Обратная косая черта экранируется; SQL и имена колонок из пользовательского ввода не принимаются.

В конструкторе не предлагаются поля `wagon_no`, `wagon_state`,
`cargo_weight_kg`, `oper_dt` и `norm_delivery_dt`. Они остаются в серверном
списке допустимых полей только для выполнения ранее сохранённых KPI. При
редактировании старой карточки такое условие сохраняется как скрытый устаревший
вариант, но выбрать его для нового условия нельзя.

Для страниц «Подход вагонов» и «Отправление вагонов» в условиях доступны
«Грузоотправитель» (`CONSIGNOR`) и «Грузополучатель» (`CONSIGNEE`). Значения
сравниваются с одноимёнными полями загруженной справки РЖД.

## API

- `POST /api/kpi/user` — создание или изменение своей карточки; для администратора `SUPER` доступно редактирование с `admin=1`.
- `DELETE /api/kpi/user/{id}` — удаление только своей пользовательской карточки.
- `GET /api/kpi/summary` — возвращает системные, нескрытые общие и личные карточки текущего пользователя.
- `POST /api/kpi/card/{id}/hide` — скрывает активную системную или общую карточку для текущего пользователя.
- `POST /api/kpi/card/{id}/restore` — возвращает скрытую системную или общую карточку.
- `GET /api/kpi/hidden` — возвращает список скрытых активных системных и общих карточек для модального окна.
- `GET /kpi/hidden` — резервная страница восстановления скрытых системных и общих карточек.
- `ApiController::dislDetail()` применяет сохранённые условия при открытии детализации и проверяет владельца.

## Действия и состояние

Включение/отключение пользовательских KPI выполняется в `/admin/kpi` ролью `SUPER`. Там же `SUPER` выбирает личную или общую область видимости, редактирует и глобально удаляет общие карточки. Неактивные карточки не возвращаются в сводный API и список восстановления. В административной таблице статус и тип показываются явно.

Изменение статуса и системных параметров в `/admin/kpi` отправляется AJAX-запросом через `KpiController::save()`. После успешного ответа статус и подпись кнопки обновляются в строке без перезагрузки страницы, поэтому поиск и фильтры сохраняются.

В карточках пользовательских KPI кнопки редактирования и удаления приведены к компактным иконкам в одной строке. Общая карточка скрывается кнопкой с перечёркнутым глазом. Список скрытых KPI открывается в модальном окне текущей страницы; отдельный URL сохранён как резервный вариант. Доступность действий не меняется.

Форма создания KPI открывается по кнопке «+» в центрированном модальном окне текущей страницы. После сохранения окно закрывается, а карточки обновляются без перехода на другую страницу. Прямой URL `/kpi/create` сохранён как резервный вариант.

Условия создаваемых и редактируемых пользовательских KPI всегда объединяются оператором `AND`. Выбор `OR` в форме отсутствует, а `UserKpiController::save()` принудительно сохраняет `AND`, независимо от данных запроса. Ранее сохранённые KPI с `OR` продолжают выполняться до их редактирования.

HTML-форма и API-действия пользовательских KPI собраны в `UserKpiController`: каталог полей, сохранение, удаление, персональное скрытие, восстановление и список скрытых карточек. URL `/api/kpi/...` сохранены; `ApiController` отвечает за расчёт сводных карточек и детализацию.

## Детализация

Для `TABLE` открывается стандартная детализация. Для группировки доступны
фиксированные шаблоны `TRAIN_NUMBER`, `TRAIN_INDEX` и `WAGON_TYPE`, определённые
в `src/Reports/KpiGroupingTemplates.php`. Системные KPI не переводятся на JSON и
сохраняют PL/SQL-логику.

## Изменения БД

Для работы административного статуса признак `IS_ACTIVE` должен быть добавлен
миграцией `db/kpi/2026-11-06-kpi-admin-active.sql`. Для страницы «Простои»
ограничение `XX_RJD_KPI_TBL_PAGE_CK` расширяется миграцией
`db/kpi/2026-11-13-allow-downtime-user-kpi.sql`. Миграции кодом приложения не
выполняются; их состояние в целевой БД нужно проверять отдельно.

## Добавление пользовательских KPI на новую страницу

Новая страница включается через реестры и общий обработчик. Отдельный экран
конструктора и отдельный JavaScript-список создавать не нужно.

### Порядок работ

1. В `src/Reports/KpiTypeRegistry.php` добавить тип с `page`, `tab`, уникальным
   `container_id`, `user_creatable = true` и списком `fields`. Подписи полей
   добавить в `FIELD_LABELS`; типы — `string`, `number` или `date`.
2. В `templates/app.php` добавить контейнер `.kpi-grid` с тем же id, что и
   `container_id`. `public/assets/js/user-kpi.js` автоматически добавит кнопку
   «+» и откроет общий `/kpi/create?kpi_type=...`; отдельную форму создавать нельзя.
3. Для отчёта проверить `src/Reports/ReportConfig.php`; для самостоятельной
   страницы добавить её в `src/Services/PageRegistry.php` и `src/routes.php`.
   Серверное право страницы обязательно.
4. Проверить `PageRegistry::kpiSourcePage()` для детализации. `app.js` обычно не
   меняется: `KPI_BOARDS` строится из `window.APP_KPI_TYPES`.
5. В `ApiController::kpiSummary()` использовать `GET_PAGE_KPI()` только если
   новый тип уже поддержан PL/SQL. Для особого источника добавить отдельный
   расчёт: выбрать доступные активные KPI, проверить `PRIVATE`/`GLOBAL`, получить
   источник без фильтров страницы, вызвать `KpiCondition::compile()`, выполнить
   агрегаты bind-параметрами и вернуть карточки. Ошибки логировать через
   `ErrorLogger::logThrowable()`.
6. В `ApiController::dislDetail()` повторно проверить `kpi_id`, владельца, тип,
   visibility и active, применить те же условия и источник, а `group_value`
   передавать только bind-параметром. Шаблоны группировки добавляются в
   `src/Reports/KpiGroupingTemplates.php`; вычисляемые поля дополнительно
   обрабатываются в `detailFieldExpression()`.
7. Кнопка карты формируется в `templates/detail.php` через `detailMapUrl()`.
   Для нового `group_field` явно проверить право `maps`, передачу `kpi_id`,
   `kpi_table=Y` и условий на `/maps`.
8. Если Oracle ограничивает `PAGE_CODE`, добавить новый код в DDL-миграцию
   `db/kpi/*.sql` и применить её до теста сохранения:

```sql
ALTER TABLE XX_ETW.XX_RJD_KPI_TBL DROP CONSTRAINT XX_RJD_KPI_TBL_PAGE_CK;
ALTER TABLE XX_ETW.XX_RJD_KPI_TBL ADD CONSTRAINT XX_RJD_KPI_TBL_PAGE_CK
CHECK (IS_SYSTEM = 'Y' OR PAGE_CODE IN ('approach', 'departure', 'downtime', 'new-page'));
```

Нельзя подменять новый `PAGE_CODE` на существующую чужую страницу.

Текущий справочник возможностей страниц создаётся миграцией
`db/kpi/2026-11-13-user-kpi-page-settings.sql`. Раздел управления находится на
`/admin/kpi`: он объединяет список карточек и переключатели разрешения создания
по страницам. `SUPER` может включать и выключать создание, но не может включить
страницу, отсутствующую в `UserKpiRegistry` или отмеченную как технически не
поддержанную.

При открытии `/admin/kpi` `UserKpiPageSettings::sync()` автоматически добавляет
в справочник новые страницы с `USER_KPI_SUPPORTED = 'Y'` и
`CREATE_ENABLED = 'N'`. Существующие флаги не перезаписываются, поэтому после
добавления нового типа KPI отдельная INSERT-миграция для строки настройки не
требуется; администратору остаётся включить страницу кнопкой.

```bash
php -l src/Reports/KpiTypeRegistry.php

node --check public/assets/js/app.js

node --check public/assets/js/user-kpi-form.js
composer check:registry
git diff --check
```

Пройти цепочку «+» → создание → сохранение → карточка → детализация →
группировка → счётчик группы → дополнительная детализация → карта. Проверить
пустой результат, `AND/OR`, обычного пользователя, `SUPER`, GLOBAL/PRIVATE,
чужую PRIVATE-карточку, CSRF, отключённую страницу и отказ без права.

### Типовые ошибки

| Ошибка | Причина | Проверка |
|---|---|---|
| Нет кнопки «+» | `user_creatable = false`, неверный `container_id`, отсутствует контейнер или выключен `user_kpi_management_enabled` | Реестр, `templates/app.php`, конфигурация и права |
| Некорректный запрос KPI | `source_page` не совпадает с `KpiTypeRegistry::page()` | `/api/kpi/summary` и `APP_KPI_TYPES` |
| Шаблон недоступен | `KpiGroupingTemplates::get()` вернул `null` | Поля исходные или разрешённые вычисляемые |
| ORA-02290 `PAGE_CK` | Constraint не знает новый `PAGE_CODE` | Применить DDL-миграцию |
| ORA-00918 | Дублируется alias в `SELECT *` | Убрать повторное имя или использовать отдельное выражение |
| Карточка пустая | Нет дат, доступа организации, KPI скрыт/неактивен или условие не совпало | Даты, `Organizations`, hidden, `WHERE_CONFIG` |
| Не работают условия | Поле/оператор не зарегистрирован или неверный тип | `KpiTypeRegistry::fields()` и `KpiCondition::compile()` |
| В KPI попали фильтры страницы | Источник собран из query-параметров экрана | Создавать источник без экранных параметров |
| Неверная группа | `group_value` склеен в SQL или не применён `group_field` | Шаблон и bind `:user_group_value` |
| Нет карты | Нет права `maps` или `group_field` не разрешён в `detailMapUrl()` | Права, `/maps`, `kpi_id`, `kpi_table=Y` |
| Видны SQL/stack trace | Исключение возвращено напрямую | `ErrorLogger::logThrowable()` и безопасный ответ |
| Сохранение проходит, расчёт падает | Источник или SQL не соответствуют справке | Источник, aliases, ограничения организации и DDL |
