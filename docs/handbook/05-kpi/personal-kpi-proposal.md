# Личные карточки KPI

## Цель

Пользователь может собрать собственные карточки KPI для каждой доступной страницы. Личная карточка видна только создавшему её пользователю и не изменяет системные KPI.

## Где хранятся настройки

Системные KPI остаются в текущем источнике Oracle (`XX_RJD_KPI_TBL_V` и пакет `XX_RJD_DISLOCATION_NEW_PKG`). Пользовательские KPI хранятся в отдельных таблицах Oracle, чтобы обновление системной конфигурации не перезаписывалo пользовательские настройки.

Минимальная таблица `XX_RJD_USER_KPI` хранит владельца, страницу, название, источник, показатель, JSON-конфигурацию группировки, порядок и дату изменения. Владелец определяется по текущей сессии; `user_id` нельзя принимать из формы.

## Единые источники истины

`src/Reports/ReportConfig.php` описывает доступные страницы, отчёты, фильтры, поля и стандартную детализацию. Он не хранит личные значения пользователей.

Отдельный каталог, например `src/Reports/KpiCatalog.php`, содержит разрешённые источники данных, показатели, поля группировки, секции и конечные страницы детализации. Пользователь выбирает только элементы каталога. Произвольный SQL, имена таблиц и PHP-конфигурацию через UI передавать нельзя.

`PageRegistry` хранит только страницу и право доступа к конструктору и API личных KPI. Список личных карточек, их порядок и настройки не добавляются в реестр страниц.

## Видимость и доступ

По умолчанию карточка имеет режим `private` и выбирается запросом по `owner_user_id = текущий пользователь`. Сервер проверяет владельца и при чтении, изменении, удалении и открытии прямого URL. Скрытие карточки в JavaScript защитой не является.

Системные KPI и личные KPI возвращаются раздельно. Личная карточка дополнительно не расширяет права на исходный отчёт или детализацию: все серверные проверки исходной страницы и `wagon-detail` сохраняются.

## Конфигурация группировки

В JSON сохраняется только пользовательский выбор разрешённых ключей:

```json
{
  "grouping": ["train_index", "load_state"],
  "sections": ["loaded", "empty"],
  "detail": "wagon-detail"
}
```

Сервис проверяет каждый ключ через `KpiCatalog`, строит SQL с параметрами и возвращает общий формат данных. Универсальный экран показывает группы и передаёт накопленные фильтры в стандартную детализацию.

## Что потребуется реализовать

1. Добавить каталог разрешённых KPI-источников, показателей, группировок и детализаций.
2. Создать таблицу личных KPI и миграцию.
3. Добавить сервис CRUD с проверкой владельца и валидацией конфигурации.
4. Добавить защищённые API списка, создания, изменения и удаления карточек.
5. Добавить универсальный экран конструктора и отображения группировки.
6. Подключить личные карточки к каждой странице через код страницы из `PageRegistry`.
7. Добавить журналирование неожиданных ошибок БД и файлов с безопасными идентификаторами.

Порядок внедрения: сначала личные карточки без общего доступа, затем группированная детализация для одной KPI, после проверки — подключение других источников через каталог. Настройки по умолчанию, подписи и доступные поля не дублировать в шаблонах и JavaScript.

## Проверки

Перед завершением выполнить `php -l` изменённых PHP-файлов, `node --check` изменённого JavaScript, `composer check:registry` и `git diff --check`. Отдельно проверить прямой URL чужой карточки, отсутствие права на исходную детализацию, создание, изменение и удаление своей карточки.
