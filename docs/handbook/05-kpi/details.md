# Детализации KPI

## Общий принцип

Карточка может передавать в интерфейс объект `detail` с контекстом и параметрами. JavaScript использует эти данные, чтобы открыть соответствующую детализацию. Для стандартного перехода в коде `ApiController::kpiSummary()` задаётся контекст `dislocation` и параметры `kpi_id` и `train_groups`.

Специальные настройки некоторых KPI находятся в `ReportConfig::kpiDetail(string $code)`.

## Какие KPI имеют специальную группировку

В текущем коде `kpiDetail()` поддерживает:

- `formed_trains`;
- `abandoned_wagons`;
- `abandoned_trains`.

Для сформированных поездов используются поля `train_index`, а также дополнительные `operation` и `trip_start_dt`. Для брошенных поездов набор полей включает индекс, номер поезда, станцию, дорогу и дату операции.

Настройка содержит:

- `code` — код режима детализации;
- `title` — заголовок;
- `empty` — сообщение при отсутствии строк;
- `count_label` — подпись счётчика;
- `fields` — поля и форматы;
- `group_by` — ключи группировки;
- `sections` — секции и фильтры.

Для брошенных поездов секции разделяются на гружёные (`cargo_state = 'гр.'`) и порожние (`cargo_state = 'пор.'`). Для сформированных поездов есть секция вагонов.

## Где находится код

| Задача | Файл / метод |
|---|---|
| Описание KPI-детализации | `src/Reports/ReportConfig.php::kpiDetail()` |
| Подписи и форматы исходных полей | `src/Reports/source-columns.php` / `ReportConfig::sourceColumns()` |
| Получение KPI ID и выборка | `src/Controllers/ApiController.php::dislDetail()` |
| Клиентский переход и состояние | `public/assets/js/app.js`, `public/assets/js/detail-contexts.js` |
| Шаблон детализации | `templates/detail.php` |

## Как добавить новый режим детализации

1. Уточните, какой код KPI приходит из `XX_RJD_KPI_TBL_V`.
2. Определите поля, группировку, секции и фильтры.
3. Добавьте конфигурацию в `ReportConfig::kpiDetail()` или используйте уже существующий общий механизм, если он подходит.
4. Проверьте, как `ApiController::dislDetail()` интерпретирует `kpi_id` и режим группировки. Не считайте, что одной конфигурации достаточно для произвольного нового алгоритма.
5. Если нужны новые поля, добавьте их в `source-columns.php` и убедитесь, что SQL действительно возвращает эти поля.
6. Обновите клиентский обработчик только в том случае, если новый контекст отличается от существующих.
7. Проверьте соответствие количества групп/вагонов исходному KPI, фильтры, пустое состояние и навигацию назад.

## Важная проверка согласованности

Число на карточке и детализация должны опираться на одинаковые бизнес-условия. Для групповых KPI карточка может считать уникальные группы, а таблица показывать вагоны внутри групп. Поэтому сравнивать нужно соответствующую метрику: количество поездов с количеством групп, а количество вагонов — с количеством строк/вагонов.

Существующая логика для `formed_trains`, `abandoned_trains` и `abandoned_wagons` описана в `docs/логика/логика_страниц.md`. При изменении расчёта обязательно обновляйте её и тестируйте на одних и тех же параметрах/срезе данных.
