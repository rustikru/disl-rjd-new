Полный справочник ReportConfig.php : отчёты, фильтры, группировки и рассылки

Документ описывает реализацию из архива проекта от 07.11.2026. Это руководство по фактическому коду, а не список желаемых возможностей. Если ниже указано «не поддерживается», это означает, что в проверенном снимке кода соответствующая возможность не реализована полностью.

1. Для чего нужен ReportConfig.php

Файл src/Reports/ReportConfig.php содержит конфигурацию отчётных разделов. Через него приложение узнаёт:

  • как называется отчёт;
  • какие API-адреса загружают фильтры, сводку и детализацию;
  • какие поля фильтров показывать;
  • какие измерения доступны для строковой группировки;
  • какие измерения доступны для колонок сводной таблицы;
  • в каких сценариях отчёт доступен: страница, экспорт, рассылка;
  • какие методы ApiController вызываются для каждого API;
  • как подписывать и строить таблицы страницы;
  • какие столбцы показывать в детализации;
  • какой обработчик использовать при формировании рассылки.

Важно: ReportConfig не выполняет SQL и не создаёт данные отчёта. Он описывает настройки. Реальная выборка находится в методах ApiController, а построение файла рассылки — в MailingRun.

Главный метод:

$reports = ReportConfig::all();

Он возвращает ассоциативный массив. Ключ массива — стабильный код отчёта, например approach. Не меняйте этот код только ради изменения подписи на экране: он используется в маршрутах, настройках рассылок и сохранённых записях БД.

2. Конструктор self::report(): все параметры по порядку

Сигнатура из исходного файла:

private static function report(
    string $name,
    ?string $filtersEndpoint,
    ?string $summaryEndpoint,
    ?string $detailEndpoint,
    array $filters,
    array $rowDimensions = [],
    array $columnDimensions = [],
    bool $organizationRequired = true,
    bool $mailingEnabled = true,
    bool $mailingSelectable = true
): array

Параметры передаются позиционно, поэтому порядок нельзя менять.

№ Параметр Тип Значение по умолчанию Что означает
1 $name string Обязателен Название отчёта в интерфейсе и рассылках
2 $filtersEndpoint ?string Обязателен URL получения списков значений фильтров; null, если endpoint не нужен
3 $summaryEndpoint ?string Обязателен URL получения сводной таблицы; null, если сводки нет
4 $detailEndpoint ?string Обязателен URL получения подробных строк; null, если детализации нет
5 $filters array Обязателен Список фильтров, созданных через self::filter()
6 $rowDimensions array [] Измерения, по которым можно группировать строки сводной таблицы
7 $columnDimensions array [] Измерения, которые раскладывают данные по колонкам сводной таблицы
8 $organizationRequired bool true Признак, что отчёт требует выбранную организацию
9 $mailingEnabled bool true Добавлять ли отчёт в контекст mailing
10 $mailingSelectable bool true Можно ли выбирать отчёт в списке отчётов формы рассылки

Допустимые значения флагов

  • true — включено / требуется.
  • false — выключено / не требуется.

Примеры из текущего кода:

// Все три флага имеют значения по умолчанию:
// организация обязательна, рассылка разрешена,
// отчёт доступен для выбора в рассылке.
self::report(...);

// Отчёт можно открыть на странице и экспортировать,
// но нельзя включать в рассылки.
self::report(..., true, false, false);

// Отчёт включён в контекст рассылки, но недоступен
// для выбора пользователем в списке рассылок.
self::report(..., true, true, false);

Не путайте два последних параметра:

  • mailingEnabled управляет присутствием отчёта в ReportConfig::forContext('mailing');
  • mailingSelectable передаётся в интерфейс как selectable и управляет возможностью выбора отчёта пользователем.

3. Конструктор self::filter(): описание каждого поля фильтра

Сигнатура:

private static function filter(
    string $key,
    string $label,
    string $valueType,
    string $fieldId,
    ?string $optionsKey = null,
    array $contexts = ['page', 'mailing'],
    bool $required = false,
    array $choices = [],
    ?string $initialValue = null
): array
Параметр Тип Что означает
$key string Имя параметра, которое должно прийти в API и которое сохраняется в настройках рассылки
$label string Подпись поля для пользователя
$valueType string Тип элемента интерфейса и формат вводимого значения
$fieldId string HTML id элемента на странице отчёта
$optionsKey ?string Имя массива вариантов внутри ответа filtersEndpoint
$contexts array Сценарии, в которых показывать фильтр
$required bool Обязателен ли фильтр
$choices array Статический список допустимых значений
$initialValue ?string Специальное начальное значение для даты

3.1. $key — имя параметра

Это техническое имя фильтра. Оно связывает интерфейс, запрос API, серверную проверку и сохранённые настройки.

Например:

self::filter('cargo', 'Груз', 'select', 'fApproachCargo', 'cargo')

Здесь cargo — ключ, который должен получить сервер. Груз — только подпись на экране.

Если изменить key, необходимо проверить:

  1. JavaScript, который собирает параметры;
  2. ReportConfig::validateFilters();
  3. соответствующий метод ApiController;
  4. SQL-условие;
  5. сохранённые настройки рассылок в XX_RJD_USER_MAILING_REPORTS.

Не меняйте $key только для переименования подписи. Для этого меняют $label.

3.2. $valueType — допустимые типы

В проверенном ReportConfig.php реально используются три значения:

Значение Что создаётся Для чего
'text' Текстовое поле Номер вагона, произвольный текст
'select' Выбор из вариантов Груз, станция, род вагона
'date' Поле даты Дата начала/окончания периода

Другие типы в определениях фильтров этого архива не обнаружены. Не используйте 'number', 'checkbox', 'datetime' или 'multiselect', пока не добавлена и не проверена поддержка в интерфейсе, проверке значений и обработчиках API.

3.3. $fieldId — идентификатор HTML-поля

Например, fApproachCargo.

Он должен быть уникальным на странице и соответствовать полю, которое создаёт JavaScript. Это не имя параметра API: имя API — $key.

3.4. $optionsKey — откуда берутся варианты списка

Например:

self::filter('cargo', 'Груз', 'select', 'fApproachCargo', 'cargo')

cargo в пятом аргументе означает, что варианты берутся из массива cargo в JSON-ответе endpoint фильтров.

Пример общей формы ответа:

{
  "cargo": [
    {"value": "КИСЛОТА АЗОТНАЯ (481143)", "label": "КИСЛОТА АЗОТНАЯ (481143)"}
  ],
  "depart_station": [
    {"value": "УГЛЕУРАЛЬСКАЯ", "label": "УГЛЕУРАЛЬСКАЯ"}
  ]
}

Это пример структуры, а не утверждение, что каждый endpoint возвращает оба массива. Фактический набор ключей определяется методом ...Filters() конкретного отчёта.

Если optionsKey = null, список из endpoint не загружается. Для select можно задать статические варианты через $choices.

3.5. $contexts — где доступен фильтр

В коде используются следующие значения:

Значение Назначение
'page' Фильтр показывается на странице отчёта
'mailing' Фильтр показывается в настройках рассылки
'export' Фильтр доступен в контексте экспорта

По умолчанию:

['page', 'mailing']

Примеры:

// Только на странице:
['page']

// На странице и в рассылке:
['page', 'mailing']

// Во всех трёх контекстах:
['page', 'export', 'mailing']

ReportConfig::forContext($context) сначала отбирает отчёты по контексту, затем оставляет только те фильтры, у которых в $contexts присутствует этот контекст.

Критически важно для рассылок: наличие фильтра на странице не означает, что он автоматически появится в рассылке. Если указано ['page'], форма рассылки его не получит.

3.6. $required — обязательность

  • true — пользователь должен заполнить поле;
  • false — поле можно оставить пустым.

Для рассылки MailingService::save() проверяет обязательность фильтров через описание отчёта. Необязательный пустой фильтр не должен создавать условие отбора.

3.7. $choices — статические допустимые значения

Формат:

[
    ['value' => 'daily', 'label' => 'Каждый день'],
    ['value' => 'weekly', 'label' => 'Еженедельно'],
]
  • value — значение, которое передаётся в API и сохраняется;
  • label — подпись для пользователя.

Если choices не пустой, ReportConfig::validateFilters() проверяет, что переданное значение есть среди value.

Если choices = [], значение не сверяется со статическим списком. Для динамического select допустимость и обработка значения должны обеспечиваться серверным методом и SQL-логикой.

3.8. $initialValue — начальное значение даты

В текущем коде используются:

Значение Что означает
null Специальное начальное значение не задано
'month_start' Первое число текущего месяца
'today' Сегодняшняя дата

Эти значения обрабатываются JavaScript формы рассылки mailingInitialDate(). Это не универсальный механизм для произвольных значений: другие строки не имеют специальной обработки в этой функции.

4. Как работает множественный выбор

В текущем ReportConfig::all() признак multiple не задаётся отдельным аргументом filter().

Он вычисляется автоматически после построения отчётов:

$multipleFilters = in_array(
    $reportDefinition['navigation']['group'] ?? '',
    ['movement', 'analytics'],
    true
);

$filter['multiple'] =
    $multipleFilters && $filter['value_type'] === 'select';

Следовательно, в этом снимке множественный выбор включается только для фильтров типа select у отчётов, чья группа навигации — movement или analytics.

Группы навигации определяются в navigationSettings():

  • movement — дислокация, подход, отправление, погрузка;
  • analytics — техническое состояние, анализ периода;
  • downtime — простои, сырьё, претензии;
  • registry — контроль простоев.

Практические последствия:

  • cargo у отчёта approach получает multiple = true;
  • depart_station у approach тоже получает multiple = true на странице, потому что это select в группе movement;
  • station_code у claims не получает multiple, потому что claims находится в группе downtime.

Важное ограничение рассылки

Хотя признак multiple вычисляется для фильтра отчёта, MailingController::settingsPage() не передаёт поле multiple в MAILING_REPORTS.

Форма templates/admin/report-mailings.php создаёт для динамического select обычное текстовое поле с подсказками. Выбор подсказки записывает одно значение в input.

Кроме того, текущий ReportConfig::validateFilters() приводит значение к строке:

$value = trim((string) ($values[$key] ?? ''));

Это не обработчик массива значений. Поэтому множественный выбор на странице и множественный выбор в рассылке — не одно и то же. В проверенном архиве полноценный мультивыбор в настройках рассылки не реализован.

Чтобы добавить мультивыбор в рассылку, недостаточно добавить 'mailing' в $contexts. Потребуется отдельно:

  1. передать multiple из MailingController в MAILING_REPORTS;
  2. создать в report-mailings.php интерфейс с несколькими выбранными значениями;
  3. изменить сохранение/чтение filters_json так, чтобы массив не превращался в строку;
  4. расширить ReportConfig::validateFilters() для массивов;
  5. проверить, что метод ApiController и SQL принимают несколько значений;
  6. проверить редактирование сохранённой рассылки и повторное восстановление всех выбранных значений.

5. self::dimension() — группировка строк

Сигнатура:

private static function dimension(string $key, string $label): array

Параметры:

  • key — имя поля/измерения, которое использует backend;
  • label — название для пользователя.

Пример:

self::dimension('oper_station', 'Станция операции')

Это означает: в списке группировок отображать «Станция операции», а в запросах и серверной логике использовать ключ oper_station.

Измерение само по себе не создаёт SQL GROUP BY. Серверный метод должен поддерживать соответствующий ключ и включать его в группировку.

6. self::columnDimension() — группировка по колонкам

Сигнатура:

private static function columnDimension(string $key, string $parameter): array
  • key — поле результата, которое будет отображаться как измерение колонок;
  • parameter — ключ параметра, через который frontend/backend выбирают соответствующую размерность.

Пример:

self::columnDimension('wagon_type_code', 'wagon_type')

Здесь wagon_type_code — поле результата, а wagon_type — параметр выбора измерения колонок.

Это не то же самое, что dimension():

  • dimension() описывает варианты группировки строк;
  • columnDimension() описывает разбиение данных по колонкам сводной таблицы.

Допустимые значения parameter не являются произвольными. Они должны совпадать с теми параметрами, которые реально обрабатывает JavaScript и метод summary конкретного отчёта. В этом проекте встречаются wagon_type и cargo_state.

7. Полный пример dislocation с расшифровкой

Исходный пример:

'dislocation' => self::report(
    'Общая дислокация',
    '/api/dislocation/filters',
    '/api/dislocation/summary',
    '/api/dislocation/detail',
    [
        self::filter('wagon_no', '№ вагона', 'text', 'fDislocationWagonNo'),
        self::filter('cargo', 'Груз', 'select', 'fDislocationCargo', 'cargo'),
    ],
    [
        self::dimension('dest_state', 'Страна назначения'),
        self::dimension('dest_road', 'Дорога назначения'),
        self::dimension('dest_station', 'Станция назначения'),
    ],
    [
        self::columnDimension('wagon_type_code', 'wagon_type'),
        self::columnDimension('cargo_w_type', 'cargo_state'),
    ],
    true,
    true,
    false
),

Читаем сверху вниз:

  1. dislocation — внутренний код отчёта.
  2. 'Общая дислокация' — название.
  3. /api/dislocation/filters — откуда брать варианты фильтров.
  4. /api/dislocation/summary — endpoint сводной таблицы.
  5. /api/dislocation/detail — endpoint подробных строк.
  6. Первый фильтр — текстовый поиск по номеру вагона.
  7. Второй фильтр — список грузов, варианты берутся из ключа cargo.
  8. Строки можно группировать по стране, дороге и станции назначения.
  9. Колонки можно строить по роду вагона или состоянию груза.
  10. true — отчёту нужна организация.
  11. true — отчёт входит в контекст рассылки.
  12. false — отчёт не предлагается пользователю для выбора в списке рассылок.

Последние три значения нельзя пропускать или переставлять местами без понимания их назначения.

8. Дополнительные настройки внутри ReportConfig::all()

После объявления $reports метод дополняет каждый отчёт данными из отдельных методов.

navigationSettings()

Формат:

'report-code' => ['group' => 'movement', 'order' => 20]
  • group — группа навигации; в текущем коде используются movement, analytics, downtime, registry;
  • order — числовой порядок внутри группы.

Группа влияет не только на меню: по ней также вычисляется multiple у select-фильтров.

apiHandlers()

Связывает тип endpoint с методом ApiController:

'approach' => [
    'filters' => 'approachFilters',
    'summary' => 'approachSummary',
    'detail' => 'approachDetail'
]

Ключи внутри записи:

  • filters — метод, который возвращает варианты фильтров;
  • summary — метод сводной таблицы;
  • detail — метод детализации.

Endpoint в self::report() и имя метода в apiHandlers() должны соответствовать друг другу. Если endpoint задан, но обработчик не зарегистрирован или назван иначе, маршрут не будет работать корректно.

mailingHandlers()

Связывает код отчёта с методом ApiController, который формирует строки для рассылки:

'approach' => 'approachDetail'

MailingRun вызывает этот метод напрямую, передавая сохранённые фильтры как query-параметры. Для отчёта, доступного в рассылке, должна существовать соответствующая запись обработчика.

pageSettings()

Содержит настройки конкретного HTML-интерфейса:

  • имена файлов экспорта;
  • текст итогов и подзаголовков;
  • ID HTML-таблиц и панелей;
  • ключи состояния загрузки;
  • ID кнопок «Применить» и «Сбросить»;
  • специальные переопределения для организации;
  • дополнительные колонки и поведение страницы.

Это не параметры SQL. Значения ID должны совпадать с элементами соответствующего шаблона и использоваться клиентским кодом.

detailSettings() и detailTabs()

detailSettings() задаёт:

  • подпись детализации;
  • сортировку по умолчанию;
  • набор колонок детализации.

detailTabs() задаёт вкладки карточки детализации. В текущем коде:

  • main — «Основная информация»;
  • data-wagon — «Данные о вагоне»;
  • disl-wagon — «Дислокация вагона»;
  • techn-state-wagon — «Техн. состояние».

Колонки детализации формируются из baseColumns(), approachExtraColumns(), lesseeColumns() и других методов этого же класса. Подробный список ключей нужно сверять с соответствующими методами, а не придумывать новые ключи в настройке отчёта.

9. Методы ReportConfig, которые должен знать разработчик

Метод Назначение Когда использовать
all() Получить все определения отчётов Общий реестр
forContext($context) Получить отчёты и фильтры для сценария Страница или рассылка
find($reportCode) Найти один отчёт по коду Когда известен код
validateFilters($reportCode, $values, $require) Проверить и нормализовать значения фильтров Перед выполнением отчёта
kpiDetail($code) Получить конфигурацию специальных KPI-детализаций KPI по известному коду
trainGroups($profile, $title, $empty) Получить конфигурацию группировки поездов Группировки поездов

Для forContext() в коде используются:

  • page;
  • export;
  • mailing.

Другие значения не следует использовать без расширения кода.

Ограничения validateFilters()

Текущая реализация:

  • принимает значения как скалярные строки;
  • проверяет обязательность;
  • проверяет формат даты YYYY-MM-DD;
  • проверяет статические choices;
  • пропускает пустые необязательные поля.

Она не реализует полноценную проверку массива множественного выбора. При добавлении мультивыбора нужно менять и эту функцию, а не только интерфейс.

10. Как фильтр проходит от страницы до Oracle

Для отчёта approach путь выглядит так:

  1. ReportConfig::all() описывает фильтр.
  2. ReportConfig::forContext('page') оставляет фильтры для страницы.
  3. Frontend строит поле и собирает его значение по key.
  4. Браузер отправляет параметр в /api/approach/summary или /api/approach/detail.
  5. Маршрут в src/routes.php определяет API-метод через apiHandlers().
  6. ReportConfig::validateFilters() проверяет параметры.
  7. ApiController::approachSummary() или approachDetail() формирует выборку.
  8. SQL применяет фильтры к Oracle.

Для рассылки путь другой:

  1. ReportConfig::forContext('mailing') отбирает отчёты и фильтры для рассылки.
  2. MailingController::settingsPage() передаёт описание фильтров в шаблон.
  3. templates/admin/report-mailings.php строит поля и отправляет форму.
  4. MailingService::save() проверяет и сохраняет отчёт и filters_json.
  5. MailingRun::runReports() получает сохранённые фильтры.
  6. MailingRun вызывает обработчик из mailingHandlers() в ApiController.
  7. ApiController формирует строки, затем MailingRun записывает XLSX.

11. Как правильно добавить новый фильтр на страницу и в рассылку

Пример: добавляем фильтр «Станция отправления» в отчёт approach.

Шаг 1. Определить ключ и тип

  • ключ: depart_station;
  • подпись: Станция отправления;
  • тип: select;
  • HTML ID: fDepartStation;
  • ключ вариантов: depart_station.

Шаг 2. Указать контексты

Только страница:

self::filter(
    'depart_station',
    'Станция отправления',
    'select',
    'fDepartStation',
    'depart_station',
    ['page']
)

Страница и рассылка:

self::filter(
    'depart_station',
    'Станция отправления',
    'select',
    'fDepartStation',
    'depart_station',
    ['page', 'mailing']
)

Но второй вариант не делает рассылку множественной. Текущая форма рассылки поддерживает одно значение для динамического списка.

Шаг 3. Добавить варианты в API

В ApiController::approachFilters() должен возвращаться ключ depart_station с допустимыми вариантами.

Шаг 4. Применить фильтр в запросе

В approachSummary()/approachDetail() или общем методе построения выборки должен использоваться параметр depart_station. Проверяйте не только передачу параметра в URL, но и фактически сформированный SQL.

Шаг 5. Проверить рассылку

Если фильтр включён в контекст mailing, проверьте:

  • отображение поля в форме;
  • сохранение значения;
  • повторное открытие формы;
  • передачу значения в MailingRun;
  • наличие условия в SQL при формировании файла.

Шаг 6. Если нужен множественный выбор в рассылке

Это отдельная доработка формы, сохранения и серверной валидации. Не считать задачу завершённой только после добавления 'mailing' в $contexts.

php -l src/Reports/ReportConfig.php
php -l src/Controllers/ApiController.php
php -l src/Controllers/MailingController.php
php -l src/Services/MailingService.php

composer check:registry

Затем проверьте вручную:

  1. Отчёт открывается на странице.
  2. Фильтр отображается в правильном контексте.
  3. Выбранное значение присутствует в Network-запросе.
  4. Фактический SQL содержит условие фильтра.
  5. Детализация использует те же ограничения.
  6. При включённом контексте mailing поле появляется в форме рассылки.
  7. Значение сохраняется и восстанавливается при редактировании.
  8. Тестовая рассылка формирует файл с ожидаемым количеством строк.

Не отмечайте проверку как пройденную, если проверили только PHP-синтаксис.
