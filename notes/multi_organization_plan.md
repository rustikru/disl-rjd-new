# План внедрения поддержки нескольких организаций

## Цель

Перевести приложение с работы в контексте одной организации на работу с несколькими организациями без разделения данных по разным таблицам и без создания отдельных копий приложения.

Основные правила:

- одна загружаемая справка относится только к одной организации;
- организация определяется источником справки или выбором при загрузке, а не содержимым отдельных строк;
- все строки справки получают один `organization_id`;
- пользователь может иметь доступ к одной или нескольким организациям;
- одна из доступных организаций является организацией по умолчанию;
- роли отвечают за доступ к разделам и действиям;
- связь пользователя с организацией отвечает за доступ к данным;
- последняя справка определяется в разрезе `organization_id + type_reference + report_dt`;
- строки дислокации без `organization_id` после завершения миграции не допускаются.

## Этап 0. Зафиксировать бизнес-правила

До начала реализации необходимо подтвердить:

1. Одна справка всегда принадлежит только одной организации.
2. Организация назначается всей справке во время импорта.
3. Пользователь может просматривать одну или несколько организаций.
4. Пользователь с несколькими организациями может переключать активную организацию.
5. Пользователь с одной организацией работает с ней автоматически.
6. Администратор также работает в контексте выбранной организации при просмотре рабочих данных.
7. Импорт разрешён только пользователям:
   - имеющим роль с доступом к странице импорта;
   - имеющим `can_import = 1` для выбранной организации.
8. Неактивные организации нельзя выбирать и использовать для новых загрузок.

## Этап 1. Изменить структуру базы данных

### 1.1. Создать справочник организаций

Предлагаемая таблица:

```sql
CREATE TABLE xx_rjd_organizations (
    id          NUMBER NOT NULL,
    code        VARCHAR2(50) NOT NULL,
    name        VARCHAR2(300) NOT NULL,
    short_name  VARCHAR2(150),
    is_active   NUMBER(1) DEFAULT 1 NOT NULL,
    created_at  DATE DEFAULT SYSDATE NOT NULL,

    CONSTRAINT pk_xx_rjd_organizations PRIMARY KEY (id),
    CONSTRAINT uq_xx_rjd_organizations_code UNIQUE (code)
);
```

Для `id` создать последовательность и триггер по аналогии с существующими справочниками.

### 1.2. Создать связь пользователей с организациями

```sql
CREATE TABLE xx_rjd_user_organizations (
    user_id          NUMBER NOT NULL,
    organization_id  NUMBER NOT NULL,
    is_default       NUMBER(1) DEFAULT 0 NOT NULL,
    can_import       NUMBER(1) DEFAULT 0 NOT NULL,

    CONSTRAINT pk_xx_rjd_user_orgs
        PRIMARY KEY (user_id, organization_id),

    CONSTRAINT fk_xx_rjd_user_orgs_user
        FOREIGN KEY (user_id)
        REFERENCES xx_rjd_users(id)
        ON DELETE CASCADE,

    CONSTRAINT fk_xx_rjd_user_orgs_org
        FOREIGN KEY (organization_id)
        REFERENCES xx_rjd_organizations(id)
);
```

Необходимо обеспечить, чтобы у пользователя было не более одной организации с `is_default = 1`.

### 1.3. Добавить организацию в таблицу дислокации

На период миграции поле должно допускать `NULL`:

```sql
ALTER TABLE xx_dislocation_rjd
ADD organization_id NUMBER;
```

Добавить внешний ключ:

```sql
ALTER TABLE xx_dislocation_rjd
ADD CONSTRAINT fk_xx_disl_org
FOREIGN KEY (organization_id)
REFERENCES xx_rjd_organizations(id);
```

### 1.4. Создать текущую организацию

```sql
INSERT INTO xx_rjd_organizations (
    code,
    name,
    short_name
)
VALUES (
    'METAFRAX_CHEMICALS',
    'АО "МЕТАФРАКС КЕМИКАЛС"',
    'Метафракс Кемикалс'
);
```

### 1.5. Привязать существующие данные

```sql
UPDATE xx_dislocation_rjd
SET organization_id = :metafrax_id
WHERE organization_id IS NULL;
```

Проверка:

```sql
SELECT COUNT(*)
FROM xx_dislocation_rjd
WHERE organization_id IS NULL;
```

После успешной проверки:

```sql
ALTER TABLE xx_dislocation_rjd
MODIFY organization_id NOT NULL;
```

Ограничение `NOT NULL` следует включать только после выкладки кода, который всегда передаёт организацию при импорте.

### 1.6. Привязать существующих пользователей

Всем действующим пользователям назначить Метафракс как организацию по умолчанию. Право импорта выдать администраторам и операторам либо назначить вручную.

### 1.7. Добавить индекс

Основной индекс:

```sql
CREATE INDEX ix_xx_disl_org_type_dt
ON xx_dislocation_rjd (
    organization_id,
    type_reference,
    report_dt
);
```

Дополнительные индексы создавать после проверки реальных планов выполнения запросов.

### Результат этапа

- существующие данные относятся к Метафраксу;
- существующие пользователи сохраняют доступ;
- структура готова к загрузке данных других организаций.

## Этап 2. Реализовать серверный контекст организации

Создать сервис:

```text
src/Services/OrganizationContext.php
```

Ответственность сервиса:

- получить доступные пользователю организации;
- определить организацию по умолчанию;
- определить активную организацию;
- проверить доступ пользователя к выбранной организации;
- проверить право импорта;
- переключить активную организацию;
- сбросить недоступную или отключённую организацию.

Предлагаемый интерфейс:

```php
final class OrganizationContext
{
    public function getAvailableOrganizations(int $userId): array;

    public function getActiveOrganizationId(int $userId): int;

    public function setActiveOrganization(
        int $userId,
        int $organizationId
    ): void;

    public function canImport(
        int $userId,
        int $organizationId
    ): bool;
}
```

В сессии хранить:

```php
$_SESSION['active_organization_id']
```

Источник истины о доступах — база данных. Значение из сессии или запроса всегда проверяется по `xx_rjd_user_organizations`.

Если пользователю не назначена организация, возвращать `403` и понятное сообщение.

## Этап 3. Сделать импорт организационно-зависимым

### 3.1. Определить организацию загрузки

- при одной доступной организации выбирать её автоматически;
- при нескольких показывать выбор организации;
- сервером проверять право `can_import`;
- для автоматической загрузки закреплять `organization_id` в настройках источника.

Не определять организацию по имени файла.

### 3.2. Изменить вставку данных

Добавить `organization_id` в `INSERT`:

```sql
INSERT INTO xx_dislocation_rjd (
    organization_id,
    report_dt,
    type_reference,
    ...
)
VALUES (
    :organization_id,
    :report_dt,
    :type_reference,
    ...
);
```

### 3.3. Изменить повторную загрузку

Удаление существующей версии справки обязательно должно учитывать организацию:

```sql
DELETE FROM xx_dislocation_rjd
WHERE organization_id = :organization_id
  AND report_dt = :report_dt
  AND type_reference = :type_reference;
```

Иначе загрузка одной организации может удалить данные другой.

### 3.4. Изменить проверки дубликатов

Контекст справки:

```text
organization_id + type_reference + report_dt
```

Если проверяются отдельные строки, дополнительно использовать номер вагона или другой фактический идентификатор строки.

### Результат этапа

Все новые данные гарантированно получают правильный `organization_id`.

## Этап 4. Ограничить API активной организацией

Передавать активную организацию в `ApiController` и хранить её как обязательное свойство:

```php
private int $organizationId;
```

### 4.1. Изменить `getReportDt()`

Определять последнюю дату только внутри активной организации:

```sql
SELECT MAX(report_dt) AS dt
FROM xx_dislocation_rjd
WHERE organization_id = :organization_id
```

При наличии типа справки:

```sql
AND type_reference = :type_ref
```

### 4.2. Изменить `getLatestDtsByType()`

```sql
SELECT type_reference, MAX(report_dt) AS dt
FROM xx_dislocation_rjd
WHERE organization_id = :organization_id
GROUP BY type_reference;
```

При переданном перечне типов добавить `type_reference IN (...)`.

### 4.3. Ограничить все базовые источники

Добавить организационный фильтр в:

- `dislFrom()`;
- `approachFrom()`;
- `departureFrom()`;
- `loadingFrom()`;
- `rawFrom()`;
- `downtimeFrom()`.

Условие:

```sql
AND organization_id = :organization_id
```

Фильтр обязателен даже после правильного определения даты: у разных организаций может быть одинаковая `report_dt`.

### 4.4. Исправить прямые запросы

Проверить и изменить запросы, обходящие методы `*From()`:

- прямой `MAX(report_dt)` для KPI;
- список загруженных справок;
- количество строк по датам и типам;
- фильтры;
- анализ периода;
- экспорт;
- другие прямые обращения к `xx_dislocation_rjd`.

### Результат этапа

Пользователь не может получить данные другой организации через рабочие API.

## Этап 5. Ограничить карту, KPI и вспомогательные разделы

### 5.1. Карта

В запрос карты добавить:

```sql
AND xdr.organization_id = :organization_id
```

Функция получения станций без координат также должна работать в контексте организации.

### 5.2. KPI и Oracle-пакет

Текущие KPI-функции Oracle используют общую таблицу дислокации. Необходимо передавать в них `p_organization_id` либо перенести расчёт на организационно-отфильтрованный источник.

Все внутренние запросы KPI должны содержать:

```sql
AND organization_id = p_organization_id
```

Карточка KPI и её детализация должны возвращать данные одной организации и совпадать по количеству.

### 5.3. Контроль простоев

Определить, являются ли данные `xx_disl_idle_control_v` общими для нескольких организаций. Если да, добавить организационный контекст в исходную таблицу или корректную связь с организационной дислокацией.

### Результат этапа

Карта, KPI, простои и вспомогательные разделы согласованы с основной дислокацией.

## Этап 6. Добавить администрирование организаций

### 6.1. Страница организаций

Новый раздел:

```text
Администрирование → Справочники → Организации
```

Предлагаемые маршруты:

```text
GET  /admin/directories/organizations
POST /admin/directories/organizations/save
POST /admin/directories/organizations/active
```

Возможности:

- создание;
- изменение названия и кода;
- включение и отключение;
- просмотр количества пользователей;
- просмотр количества загруженных справок.

Организации с историческими данными физически не удалять, а отключать через `is_active`.

### 6.2. Расширить страницу пользователей

Добавить:

- перечень доступных организаций;
- организацию по умолчанию;
- право импорта для каждой организации.

При сохранении проверять:

- организация по умолчанию входит в доступные;
- выбрана не более чем одна организация по умолчанию;
- недоступная организация не может иметь `can_import = 1`.

### Результат этапа

Администратор управляет организациями и доступами без ручных SQL-операций.

## Этап 7. Добавить переключатель организации

Разместить переключатель в общей шапке рядом с пользователем.

Endpoint:

```http
POST /api/context/organization
```

Пример тела:

```json
{
  "organization_id": 2
}
```

Сервер должен:

1. определить текущего пользователя;
2. проверить его доступ к организации;
3. проверить активность организации;
4. сохранить организацию в сессии;
5. вернуть выбранный контекст.

После переключения на первом этапе достаточно полной перезагрузки страницы.

Если пользователю доступна одна организация, показывать её название без раскрывающегося списка.

### Результат этапа

Пользователь с несколькими доступами может переключать организационный контекст.

## Этап 8. Тестирование

Обязательные сценарии:

1. Пользователь организации №1 видит только её строки.
2. Пользователь организации №2 видит только её строки.
3. Пользователь с двумя организациями может переключаться.
4. Подмена `organization_id` в запросе не открывает чужие данные.
5. Пользователь без `can_import` не может загрузить файл.
6. Повторная загрузка организации №1 не удаляет данные организации №2.
7. Одинаковая `report_dt` у двух организаций не смешивает данные.
8. Последняя дата определяется отдельно для каждого типа и организации.
9. KPI совпадает со своей детализацией.
10. Карта совпадает со сводной.
11. Экспорт содержит только выбранную организацию.
12. После отзыва доступа активная организация пользователя сбрасывается.
13. Пользователь без организации получает `403`.
14. Неактивную организацию нельзя выбрать или использовать для импорта.

Контрольный набор данных:

```text
Организация 1:
  Подход   — 30.07.2026 10:00
  Отправка — 30.07.2026 09:00

Организация 2:
  Подход   — 29.07.2026 15:00
  Отправка — 30.07.2026 11:00
```

Такой набор позволяет обнаружить глобальное определение последних дат и смешивание организаций.

## Этап 9. Порядок безопасной выкладки

1. Сделать резервную копию данных дислокации.
2. Создать справочник организаций и таблицу пользовательских доступов.
3. Добавить nullable-поле `organization_id`.
4. Создать организацию Метафракс.
5. Заполнить `organization_id` существующих строк.
6. Привязать существующих пользователей.
7. Выложить серверный контекст организации.
8. Выложить организационно-зависимый импорт.
9. Выложить фильтрацию API, карты и KPI.
10. Проверить приложение под администратором, оператором и наблюдателем.
11. Убедиться, что строк с `organization_id IS NULL` нет.
12. Сделать поле `organization_id` обязательным.
13. Создать и проверить индексы.
14. Добавить административный интерфейс и переключатель.
15. Только после проверки подключать вторую организацию.

## Рекомендуемая разбивка на релизы

### Релиз 1. Подготовка данных

- таблица организаций;
- таблица доступов пользователей;
- `organization_id` в дислокации;
- миграция существующих данных;
- привязка существующих пользователей;
- внешнее поведение приложения не меняется.

### Релиз 2. Серверное разделение

- `OrganizationContext`;
- организационно-зависимый импорт;
- фильтрация всех API;
- определение последних дат по организации;
- карта;
- KPI;
- контроль простоев;
- тесты безопасности.

После этого релиза можно безопасно хранить данные нескольких организаций.

### Релиз 3. Пользовательский интерфейс

- справочник организаций;
- назначение организаций пользователям;
- управление правом импорта;
- переключатель организации;
- диагностическая информация по загрузкам.

## Критерий готовности

Поддержка нескольких организаций считается внедрённой, если:

- каждая строка дислокации имеет `organization_id`;
- каждый запрос рабочих данных ограничен активной организацией;
- дата последней справки определяется по организации и типу;
- импорт и повторная загрузка не затрагивают другие организации;
- пользователь не может выбрать или запросить недоступную организацию;
- сводные, детализация, KPI, карта и экспорт показывают согласованные данные;
- подключение новой организации выполняется через справочник и назначение доступов, без изменения программного кода.
