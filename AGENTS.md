# Правила разработки проекта

Этот файл — обязательная памятка для разработчиков и ИИ. Перед изменением
проекта нужно прочитать его и документы, на которые он ссылается.

## Главный принцип

Код должен быть простым и понятным человеку, который впервые открыл файл.
Не усложнять решение ради архитектуры, шаблонов проектирования или «красивых»
абстракций. Сначала изучить соседний код и продолжить его стиль.

## Имена

- Использовать короткие, обычные и точные английские имена.
- Имя должно отвечать на вопрос, что хранится или что делает код: `$user`,
  `$roles`, `$page`, `$report`, `$canEdit`, `saveRole()`, `findUser()`.
- Для булевых значений использовать `is`, `has`, `can`: `$isNew`, `$hasAccess`,
  `$canDelete`.
- Не использовать искусственно сложные имена вроде
  `$pageRenderingConfigurationManager`, если достаточно `$page` или `$config`.
- Не добавлять слова `Manager`, `Processor`, `Resolver`, `Builder`, `Renderer`,
  `Handler`, `Helper`, `Provider` без реальной необходимости и принятого в
  существующем коде смысла.
- Не сокращать до непонятных букв. Допустимы только привычные в текущем месте
  имена: `$db`, `$id`, `$url`, `$api`, `$req`, `$res`.
- Файлы и методы называть по предмету: `roles.php`, `saveRole()`, `PageRegistry`.
- Стабильные коды страниц и отчётов писать в `kebab-case`: `wagon-detail`.
- Имена PHP-классов — `PascalCase`, методы и переменные — `camelCase`, CSS-классы
  — `kebab-case`. Названия таблиц и колонок сохраняют стиль БД.

## Стиль кода

- Перед правкой посмотреть весь изменяемый блок и соседние похожие файлы.
- Сохранять стиль текущего файла: отступы, переносы, кавычки, порядок методов и
  способ формирования ответа. Не форматировать весь файл из-за одной правки.
- Делать минимальное изменение, которое полностью решает задачу.
- Не создавать новый слой, класс или функцию для одноразовой простой операции.
- Повторяющиеся данные и бизнес-правила выносить в существующий единый реестр.
  Серверную проверку безопасности не удалять, даже если такая проверка есть в UI.
- Все данные из запроса проверять на сервере. Вывод в HTML экранировать через
  `htmlspecialchars()`. SQL выполнять с параметрами, без склейки пользовательских
  значений.
- POST-действия должны проверять CSRF, права пользователя и допустимость объекта.
- Не показывать пользователю исключения, SQL, пароли, настройки подключения и
  stack trace. Технические ошибки записываются в журнал и получают код ошибки.
- Не менять чужие несвязанные правки в рабочем дереве.

## Комментарии

- Комментарии писать по-русски, коротко и по делу.
- Объяснять причину, ограничение или неочевидное правило, а не пересказывать код.
- Хорошо: `// SUPER нельзя изменять через обычную форму роли.`
- Плохо: `// Получаем пользователя` перед `$user = ...`.
- Удалять устаревший комментарий вместе с изменением логики.
- Для публичного метода добавлять PHPDoc только когда он поясняет контракт,
  формат массива, исключение или неочевидное поведение.
- Не оставлять в коде историю обсуждения, черновики и длинные объяснения. Такие
  сведения помещать в `docs/`.

## Оформление страниц

- Использовать общие компоненты из `public/assets/css/app.css`: `ui-page-head`,
  `ui-page-title`, `ui-panel`, `ui-card`, `ui-table`, `ui-fields`, `ui-field`,
  `ui-form-actions`, `btn`, `ui-back-link` и другие существующие классы.
- Новая страница должна визуально повторять ближайшую существующую страницу.
  Список сравнивать со списком, форму — с формой, карточку — с карточкой.
- Формы должны оставаться компактными. Для них использовать `ui-form-page` и
  `ui-page-head--form`; не увеличивать без причины отступы, заголовки и поля.
- Кнопки выравнивать в одной строке действий. Опасное действие отделять слева,
  основные кнопки «Отмена/Сохранить» располагать справа.
- Не дублировать общие CSS-правила внутри шаблона. Локальный `<style>` допустим
  только для уникальных деталей страницы и должен быть небольшим.
- Не использовать inline-стили для повторяющихся элементов.
- Проверять длинные названия, пустые состояния, ошибки, режим только для чтения,
  узкий экран и отсутствие права на действие.
- После визуальной правки открыть страницу и проверить ровность, размеры,
  переносы и положение кнопок, а не ограничиваться проверкой синтаксиса.

## Единые источники истины

- Страницы, права, видимость и меню: `src/Services/PageRegistry.php`.
- Отчёты, endpoints, фильтры и колонки: `src/Reports/ReportConfig.php`.
- Исходные колонки справки РЖД: `src/Reports/source-columns.php`.
- Структура карточки вагона: `src/Reports/WagonConfig.php`.
- Параметры, типы, значения по умолчанию и ограничения: `ConfigSchema`.
- Не повторять эти определения в контроллерах, JavaScript и шаблонах.
- Подробности: `docs/single-source-of-truth.md`.
- Добавление самостоятельной страницы: `docs/adding-page.md`.

## Доступ и роли

- Только `SUPER` имеет безусловный доступ ко всем страницам.
- `ADMIN` получает страницы из назначенных ролей, как и остальные пользователи.
- Наличие ссылки или скрытие кнопки не является защитой. Каждый WEB, POST и API
  маршрут должен быть защищён серверным middleware и проверками действия.
- Для самостоятельной функции создавать отдельное право. Не привязывать доступ
  к случайному пункту меню, из которого пользователь открыл функцию.
- Общее API может иметь несколько разрешающих прав только через явно описанное
  правило в `PageRegistry::accessPages()`.

## Проверка перед завершением

Выполнить проверки, подходящие изменению:

```bash
php -l путь/к/изменённому.php
node --check public/assets/js/изменённый.js
composer check:registry
git diff --check
```

Также проверить прямой URL без права, работу с нужным правом, POST/API, отключение
страницы и внешний вид. Если проверка не выполнена из-за недоступной БД или
окружения, сообщить об этом явно.
